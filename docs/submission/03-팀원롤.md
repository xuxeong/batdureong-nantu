## 협업 · 분업 방식

### 폴더 경계로 충돌을 막는 구조

세 명이 12일 동안 같은 저장소에서 동시에 개발하므로, 충돌과 사고를 줄이는 것이 협업의
전제였다. 담당자별로 주 작업 폴더를 나눠, 동시에 커밋해도 같은 파일을 건드릴 일이
거의 없게 했다.

| 담당 | 주 작업 폴더 |
|---|---|
| 전성민 | `docs/planning/`, `docs/governance/`, `assets/` |
| 김민주 | `data/drafts/`, `data/candidates/` |
| 최수정 | `src/`, `tools/`, `schema/`, `api/` |

공용 파일(`data/approved/`, `docs/submission/`, `README.md`, `package.json`)은 소수로
한정하고, 고칠 때는 커밋을 작게 유지해 바로 푸시했다. 남의 영역을 건드려야 할 때는
먼저 알렸다.

충돌을 실제로 막은 것은 브랜치가 아니라 이 파일 소유 규칙이다. 두 사람이 한 브랜치에
커밋하는 것과 브랜치를 나누는 것의 충돌 양상은 같기 때문이다. `develop`/`main` 분리는
충돌 방지가 아니라 다른 목적 — 개발은 전부 `develop`에서 하고 `main`을 "언제 열어도
시연 가능한 안정판"으로 고정해, 촬영 중 누가 `develop`에 푸시해도 촬영용 URL이 깨지지
않게 하려는 것이다.

### 결정 로그 기반 협업

기획 결정을 `DEC-` ID를 가진 항목으로 관리하고, 확정·보류·폐기 상태를 명시했다.
구현이나 콘텐츠 작업 중 규칙이 모호하거나 충돌하면 임의로 우회하지 않고 작업을 멈춘 뒤
기획 책임자의 확정을 받고 재개했다.

### 작업 기록 자동화

커밋 이력에서 `PROGRESS.md`를 자동 생성하고, 커밋 메시지에 담기 어려운 맥락은
개인별 세션 로그에 남겼다. 담당자 사이의 인계는 각자의 AI 비서가 메시지 초안을 쓰고
사람이 전달한 뒤, 그 결정을 `docs/progress/`의 인계 문서(`AI_인계_2026-08-06.md`,
`handoff-*.md`)로 회수해 남겼다. (AI 활용 방식은 「AI 활용 기술 문서」 8절 참조.)

실제 협업에서는 담당 영역에서 문제가 발견되면 다른 영역을 임의로 고치지 않고 인계했다.
예를 들어 최수정이 튜토리얼 순서와 확정 DEC의 충돌을 발견하자 구현을 멈추고 사례와 대안을
전성민에게 전달했다. 전성민은 기존 DEC 두 개를 폐기·대체해 순서 규칙을 승인 데이터로
옮겼고, 최수정은 스키마·검증·주석을 동기화했다. 이후 플레이 테스트에서 남은 자원 의존
문제를 찾아 김민주에게 데이터와 튜토리얼 마무리 작업을 인계했다.

아트도 같은 방식으로 연결했다. 전성민이 확정 목업과 통합 시트, 논리 에셋 ID를 준비하면
최수정이 렌더 계층과 HUD에 연결하고, 김민주가 실제 정비·대화 화면에서 정보와 조작이 맞는지
확인했다. Git 커밋과 개인별 세션 로그에 성공 결과뿐 아니라 실패한 시도와 판단 이유도 남겨,
다음 사람이 같은 조사를 반복하지 않게 했다.
