# AI 활용 기술 문서

> 제출 형식: PDF. 이 문서를 원본으로 두고 PDF로 내보낸다.
> 요구 항목: AI 활용에 대한 기술적 설명(구조 설명, AI 대상 주요 프롬프트 및 지시 사항),
> 외부 에셋 / 오픈소스 출처.

## 1. 개요

밭두렁난투는 12일 동안 세 명이 제작한 웹 게임 프로토타입이다. AI를 단순히 결과물을
한 번에 생성하는 도구로 사용하지 않고, 기획 결정 추적·콘텐츠 데이터 초안과 검수·코드 구현과
테스트·아트 시안 제작에 나누어 사용했다. 사람이 결정과 승인을 맡고 AI는 저장소에 기록된
규칙과 승인 데이터를 입력으로 삼았다.

런타임에서도 LLM의 권한을 제한했다. 주민의 대사와 선택 반응, 전투 판정, 관계·공포도와
엔딩 선택은 승인 데이터와 코드가 먼저 확정한다. LLM은 그 결과를 바꾸지 않고 전날의
플레이어 일지와 엔딩 기록문만 작성한다.

## 3. 구조 — 저장소 자체를 AI 지시서로 사용

| 파일 | 역할 |
|---|---|
| `AGENTS.md` | 모든 AI가 먼저 적용하는 최상위 프로젝트 규칙 |
| `CLAUDE.md` | Claude Code 진입점. `@AGENTS.md`를 임포트한다 |
| `docs/planning/밭두렁난투_기획_결정로그_현재본.md` | 확정·보류·폐기 결정(DEC)의 단일 원본 |
| `docs/governance/document-impact-map.csv` | DEC 변경 시 영향 문서·절 매핑 |
| `schema/tables/` | 콘텐츠 CSV의 필드·자료형·참조 정의 |

짧은 일정에 여러 사람과 AI가 동시에 작업하면 같은 규칙을 서로 다르게 기억하는 문제가
가장 먼저 발생한다. 그래서 대화 기억이 아니라 저장소 자체를 다음 AI가 읽는 지시서로 만들었다.
모든 AI는 `AGENTS.md`를 먼저 읽고, 정확한 시스템 규칙은 상태와 ID를 가진 DEC에서 찾는다.
DEC와 설명 문서가 다르면 DEC가 우선하며, 답이 없으면 구현 편의로 채우지 않고
`결정되지 않음`으로 보고한다.

결정이 바뀔 때는 확정 원문을 덮어쓰지 않는다. 기존 DEC를 폐기하고 새 ID의 대체 결정을
작성하며, `document-impact-map.csv`로 파생 문서의 영향 구간만 동기화한다. 덕분에 AI가
과거 규칙을 현재 규칙으로 오해하지 않고, 왜 바뀌었는지도 Git 이력과 함께 추적할 수 있다.

## 4. 콘텐츠 제작 파이프라인

`DEC-PIPELINE-004`에서 그대로 옮김.

> AI를 활용하는 모든 콘텐츠 제작은 `콘텐츠 원본·제약 규칙 → AI 초안 → 담당자 검토 → 승인 콘텐츠 → 자동 검증 → 런타임 데이터 생성` 순서로 진행한다.
> …
> AI는 콘텐츠 초안만 작성할 수 있다.
> AI가 콘텐츠 원본, 승인 콘텐츠, 검증 규칙 또는 런타임 데이터를 직접 덮어쓸 수 없다.
> 각 콘텐츠 분야의 담당자가 검토하고 승인 상태로 전환한 콘텐츠만 자동 검증과 런타임 데이터 생성의 입력으로 사용할 수 있다.

실제 콘텐츠 제작은 다음과 같이 왕복했다.

1. 콘텐츠 담당자가 `data/drafts/`에서 작물·주민·레시피·대사 등의 값을 작성했다.
2. 정규화 도구가 ID, 상태, 버전, 참조를 검사한 승인 후보와 변경 보고서를 만들었다.
3. 사람이 후보를 검토하고 승인한 데이터만 `data/approved/`에 반영했다.
4. `data:validate`가 38개 CSV의 필수값·참조·복합 키·일정·엔딩 조건을 검사했다.
5. 검증을 통과한 승인본만 `data:build`를 거쳐 런타임 JSON으로 생성됐다.

대표 사례는 바나나를 토란으로 바꾼 작업이다. 화면에 보이는 이름과 콘텐츠 문구는 토란으로
바꾸되, 이미 여러 테이블이 참조하는 내부 ID `crop.banana`는 유지했다. AI가 참조 파급을
먼저 계산했고 사람이 최소 변경안을 선택했기 때문에 아홉 테이블의 ID를 동시에 이전하는
위험을 피했다.

또한 튜토리얼 순서를 검토하는 과정에서 확정 DEC가 실제 자원 의존 관계와 맞지 않아
진행 불가능하다는 사실을 발견했다. 구현을 임시 예외로 우회하지 않고 기존 DEC 두 개를
폐기·대체한 뒤, 순서의 단일 원본을 승인 데이터의 `step_order`로 옮기고 같은 단계가
연속하는지 자동 검증을 추가했다.

## 5. 데이터와 코드의 분리

`DEC-PIPELINE-016`에서 그대로 옮김.

> 작물, 아이템, 가격, 수량, 확률, 시간, 일차·습격 일정, 맵 좌표, 주민, 사연, 대사, 보상, 엔딩, 밸런스 수치와 그 밖의 변경 가능한 게임 데이터는 코드에 직접 하드코딩하지 않는다.
> 변경 가능한 게임 데이터의 단일 원본은 사람이 승인한 콘텐츠 데이터와 명세이며 게임 코드는 이를 읽고 검증하고 실행한다.
> 필수 데이터의 누락이나 오류를 코드 내부의 임시 기본값으로 숨기지 않고 데이터 검증 오류로 보고한다.

예를 들어 작물 성장 시간, 수확량, 가격, 플레이어 체력, 맵 좌표와 습격 일정은 모두 승인
CSV에서 읽는다. 필수 테이블이 없거나 참조가 깨지면 임시 수치로 실행하지 않고 데이터 오류
화면으로 이동한다. 거래·제작·협상·보상은 필요한 자원을 전부 검증한 뒤 한 번에 적용해,
도중 실패로 일부 자원만 사라지는 일을 막았다.

이 분리는 QA에서도 효과가 있었다. 튜토리얼의 45%가 제작 단계에서 막히는 문제는 코드
기본값을 넣지 않고 `starting_money`, 수확량, 레시피 입력 수량과 안내 순서를 함께 대조해
찾았다. 구조 검증 120건과 단위 테스트 207건이 통과해도 플레이 의미가 틀릴 수 있다는 점을
확인하고, 실제 완주 테스트를 별도 검증 단계로 유지했다.

## 6. 런타임 LLM — 엔딩 기록문과 플레이어 일지

`DEC-RESIDENT-054`에서 그대로 옮김. (구 `DEC-RESIDENT-001`을 대체 — 아래 플레이어 일지 시스템 도입으로 "엔딩 기록문에만" 문구가 낡아 폐기·대체됨)

> 주민의 사연·대사·선택지·반응·게임 판정은 모두 사전 제작된 콘텐츠와 규칙으로 처리한다.
> LLM은 주민 사연이나 대사를 생성하지 않는다.
> LLM은 플레이어의 답변을 판정하거나 주민 반응, 관계 변화, 공포도, 전투 보정, 영입과 처치 결과를 결정하지 않는다.
> LLM은 게임 시스템이 모든 결과를 확정한 뒤 엔딩 기록문을 작성하거나, 확정된 전날 기록으로 플레이어 일지를 작성하는 데만 사용한다.
> LLM이 생성한 엔딩 기록문과 플레이어 일지는 확정된 게임 결과와 런 기록을 변경할 수 없다.

`DEC-JOURNAL-001`, `DEC-JOURNAL-002`에서 그대로 옮김. (매 일차 시작 연출에 표시하는 짧은 1인칭 일지 — 숨겨진 공포도를 서사로 체감시키는 두 번째 런타임 LLM 접점)

> 매 일차 시작 연출에서 전날의 확정 사실을 기반으로 생성한 플레이어 1인칭 일지를 표시한다.
> 1일차 아침에는 전날 기록이 없으므로 일지를 생성하거나 표시하지 않는다.
> 입력은 전날 조우 결과, 변경된 관계 상태, 공포도 구간과 변화 방향, 확인한 사연 정보, 확정 플레이 기록으로 한정한다.
> 출력은 한국어 1~3문장, 200자 이하로 한다.

`DEC-CONTENT-011`에서 그대로 옮김.

> 확인하지 않은 사연 정보, 숨겨진 설정 문장, 대사 원문 전체, AI 초안, 폐기된 콘텐츠, 현재 보관함 전체, 시스템 프롬프트와 API 설정은 LLM 입력에 포함하지 않는다.
> 플레이어 이름은 명령이 아닌 인용된 데이터로 취급한다.
> LLM 출력은 `record_text` 문자열 하나만 가진 JSON 객체로 제한한다.
> 생성 실패 시 동일한 확정 입력으로 자동 재시도 1회를 수행하고 다시 실패하면 확정된 엔딩의 `fallback_record_text`를 표시한다.
> LLM 요청이 실패해도 엔딩 진행과 게임 완료를 막지 않는다.

엔딩과 일지 API는 브라우저에 키가 노출되지 않도록 Vercel 서버리스 함수에서만 호출한다.
`ANTHROPIC_API_KEY`에는 `VITE_` 접두어를 붙이지 않으며 저장소와 클라이언트 번들에 넣지 않는다.
고정 시스템 프롬프트는 코드에 복사하지 않고 `schema/ending_prompt_system.md`와
`schema/journal_prompt_system.md`를 단일 원본으로 사용한다.

요청 입력은 게임이 이미 확정한 사실만 포함한다. 확인하지 않은 사연, 전체 보관함, 폐기된
콘텐츠와 시스템 프롬프트는 전달하지 않는다. 응답은 JSON Schema로 필드 하나만 허용하고,
글자 수와 마크다운 사용 여부를 다시 검사한다. 실패하면 같은 입력으로 한 번만 재시도하고,
다시 실패하면 승인 CSV의 폴백 문장을 사용한다. 따라서 API 키나 네트워크가 없어도 런을
완료할 수 있다.

## 7. 사람과 AI의 역할 분담

| 영역 | AI | 사람 |
|---|---|---|
| 시스템 기획 | 기존 DEC 검색, 모순·누락·영향 범위와 대안 제시 | 최종안 선택, DEC 확정·보류·폐기 승인 |
| 콘텐츠 데이터 | 필드 사전, 최소 초안, ID·참조·버전 정규화와 자동 검수 | 수치·문구·밸런스 작성, 승인본 확정 |
| 구현 | 코드 초안, 테스트, 정적 검사, 누락 경로와 회귀 탐색 | 작업 범위 결정, 플레이 테스트, 병합·배포 승인 |
| 아트 | 목업·통합 시트·캐릭터 시안 생성과 수정안 | 아트 방향 결정, 시안 선택, 분리·투명화와 최종 채택 |
| 런타임 LLM | 확정 사실을 일지·엔딩 기록문으로 서술 | 입력 범위·출력 제약·폴백 승인, API 키 관리 |

## 8. 주요 프롬프트 및 지시 사항

실제 사용한 프롬프트 원본은 저장소에 그대로 보존돼 있다.

| 용도 | 위치 |
|---|---|
| 최상위 AI 작업 규칙 | `AGENTS.md` |
| 콘텐츠 제작 시작 프롬프트 | 콘텐츠 데이터 준비도 점검 문서 13절 |
| 단계별 재개 프롬프트 | 같은 문서 14절 |
| 수정본 검수 프롬프트 | 같은 문서 15절 |
| 시스템 기획 검토 프롬프트 | 같은 문서 16절 |
| 엔딩 생성 시스템 프롬프트 | `schema/ending_prompt_system.md` |
| 에셋 생성 프롬프트 | `docs/submission/CREDITS.md` |

대표 지시 사항은 다음과 같다.

```text
폐기되지 않은 확정 DEC와 승인 데이터를 구현의 입력으로 사용한다.
변경 가능한 게임 데이터는 코드에 하드코딩하지 않는다.
문서에 답이 없으면 결정되지 않음으로 보고하고 새 규칙을 몰래 만들지 않는다.
```

콘텐츠 수정본 검수에는 다음 순서를 사용했다.

```text
인코딩·헤더·값 표현을 정규화한다.
추가·삭제·변경 행을 비교하고 담당자가 수정한 콘텐츠 의도를 보존한다.
ID, kind, content_status, content_version과 참조를 검사한다.
AI가 스스로 approved 상태를 확정하거나 기존 승인본을 덮어쓰지 않는다.
```

아트 생성에서는 공통 화풍 블록과 화면별 명세를 분리하고, 이미 검증된 목업이나 시트를
`sole visual authority`로 지정했다. 여러 부품은 한 시트에서 함께 생성해 선 굵기·팔레트·
명암 단계를 맞춘 뒤 사람이 분리했다. 실제 전체 프롬프트와 반복 기록은 `CREDITS.md`와
`ART_ITERATION_LOG.md`에 보존했다.

## 9. 한계와 개선 방향

- 자동 검증은 구조·참조·범위를 잘 잡지만 “수확물을 팔고도 제작 재료가 남는가” 같은 플레이
  의미까지 전부 증명하지 못한다. 콘텐츠 조합 기반 시뮬레이션 테스트를 확대할 필요가 있다.
- AI는 긴 규칙 문서를 읽고도 관련 절을 다시 확인하지 않으면 이미 적힌 규칙을 놓쳤다.
  작업별 필수 절을 자동으로 추출해 체크리스트로 제공하는 도구가 필요하다.
- 아트 생성은 같은 프롬프트에서도 비율과 세부 스타일이 흔들린다. 한 캐릭터·한 시트를 먼저
  통과시킨 뒤 같은 설정값을 고정하는 방식으로 완화했지만 수작업 검수 비용이 남는다.
- 런타임 LLM은 네트워크와 API 상태에 의존한다. 승인 폴백으로 완주는 보장하지만, 실제 생성
  경로와 폴백 경로를 배포 전에 각각 확인해야 한다.
- 12일 일정 때문에 저장·이어하기, 키보드 UI 탐색, 애니메이션과 오디오 등은 1차 범위에서
  제외하거나 최소화했다.
