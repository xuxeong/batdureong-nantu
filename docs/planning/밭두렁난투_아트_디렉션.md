# 밭두렁난투 아트 디렉션

갱신일: 2026-08-05

이 문서는 규격이 아니라 **톤**을 정한다. 크기·형식·에셋 ID·경로처럼 바뀌면 코드가 깨지는 것은
`DEC-ART-001`이 확정했고, 이 문서는 그 안에서 **무엇이 어떻게 보여야 하는가**를 정한다.

이 문서는 DEC가 아니다. 시안을 보며 계속 고친다.

이미지 생성 AI에게 지시할 때는 12절의 프롬프트 블록을 **그대로 복사해서** 쓴다.
기억으로 다시 쓰면 세션마다 톤이 어긋난다.

---

## 1. 한 줄 방향

> **선은 굵고, 색은 메마르게, 익은 것만 밝다.**

화면은 전체적으로 채도가 낮고 조용하다. 플레이어가 지금 손대야 할 것 —
수확할 수 있는 작물 — 만 색으로 튀어나온다.

## 2. 레퍼런스와 번역

기준 레퍼런스는 **Don't Starve**다. 그대로 복제하지 않는다.

| 가져올 것 | 버릴 것 |
|---|---|
| 굵고 검은 외곽선으로 오브젝트를 배경에서 떼어내는 방식 | 고딕·음산한 정서 → **한국 시골의 메마른 정서**로 |
| 손으로 그린 듯한 비대칭 형태 | 검정에 잠긴 저명도 → **명도를 올려** 형태가 읽히게 |
| 그라데이션 없는 평면적 명암 | 길고 앙상한 비율 → **뭉툭하고 단단한** 비율로 |
| 종이에 그린 듯한 인상 | 스크래치·해칭 질감 → **면 안쪽은 깨끗하게** |

마지막 행이 가장 중요하다. 원작의 "손그림 느낌"을 **선의 노이즈**로 오해하면 안 된다.
그 스타일의 선은 굵되 **깔끔하고 확신에 찬 한 획**이다.

## 3. 판독 우선 원칙

> **밭의 상태와, 다가오는 것의 정체가 먼저 읽혀야 한다.**

낮에는 *어느 밭이 수확 가능한가*, 밤에는 *다가오는 사람이 누구인가*.
디테일보다 이 두 가지 판독이 우선이다.

- 경작지는 **네 상태**(빈 밭 / 씨앗 / 성장 중 / 수확 가능)가 멀리서도 구분돼야 한다.
- 야생동물 3종과 주민 4명은 **색이 아니라 실루엣**으로 구분돼야 한다.
- 지원 주민과 적대 주민은 즉시 구분돼야 한다 (`DEC-UI-012`).

## 4. 색 규약

### 4.1 밭 안에서 판정 색을 보호한다

- **밭 안에서 채도 높은 따뜻한 색은 수확 가능한 작물에만 쓴다.**
  성장 중인 작물, 배경, 흙, 주민 옷, 야생동물은 이 색대를 침범하지 않는다.
- 이것이 `DEC-UI-004`가 요구한 **수확 가능 표식**의 실체다.
- 바탕은 저채도의 흙, 마른 풀, 오래된 나무, 빛바랜 천 색이다.

**규약이 걸리는 곳은 밭 안이다.** 밭 바깥 띠의 HUD는 다르게 다룬다 (4.4절).

### 4.2 적대 표시에 붉은색을 쓰지 않는다

승인된 작물 넷 중 **고추와 토마토가 붉은 계열**이다. 밭 안에서 붉은색을 위험 신호로 쓰면
익은 작물과 다가오는 주민이 같은 색으로 읽힌다. 적대·위협은 **형태와 자세**로 표시한다.

이 항목은 4.4절의 UI 예외와 무관하게 유지된다. 밭 안에서 판독이 갈리는 것이 문제였고,
띠 위의 게이지는 그 판독에 끼어들지 않는다.

### 4.3 지원 주민은 밝은 테두리로 구분한다

`DEC-UI-012`가 요구한 지원·적대 구분은 **밝은 외곽 테두리 유무**로 한다.
색상 대비가 아니라 테두리라서 4.1의 판정 색을 침범하지 않는다.

### 4.4 UI는 화면에서 가장 조용하다

패널·버튼·슬롯은 무채색에 가까운 나무·한지 색으로 한다.

**재질은 용도로 나눈다 — 읽는 것은 종이, 누르는 것은 나무.**

| 용도 | 재질 |
|---|---|
| 패널, 모달, 대사창처럼 **읽는 것** | 나무 테두리 + 안쪽은 깨끗한 한지 |
| 버튼, 슬롯처럼 **누르고 담는 것** | 테두리 없이 **나무 판자 통짜** |

버튼에 한지를 넣지 않는다. 글이 많이 들어가는 면만 종이다.

**게이지 색은 4.1절의 예외다.** 체력 바는 붉은색, 임박한 재배 시간도 붉은 강조를 쓴다.
2026-08-05에 정했다. 전부 바랜 색으로 맞추면 화면이 지나치게 밋밋해지고, 체력이 붉은 것은
플레이어가 기대하는 관습이다.

밭 바깥 띠에 있어서 밭 안의 판정 색과 같은 화면에서 경쟁하지 않는다는 것이 근거다.
**틀과 판은 여전히 무채색 나무다.** 예외는 게이지가 차 있는 면에만 해당한다.

4.5절 색표가 채워지면 실제 값을 다시 볼 수 있다. 밭이 전부 익었을 때 화면을 보고
판단한다.

### 4.5 확정 대기 — 시안이 나온 뒤 채운다

시안에서 뽑아낸 실제 값을 여기 적는다. 그 뒤로는 이 표가 기준이다.

| 용도 | 색 코드 |
|---|---|
| 흙 (빈 경작지) | *미정* |
| 마른 풀 (배경 바닥) | *미정* |
| 성장 중 작물 | *미정* |
| **수확 가능 작물 (판정 색)** | *미정* |
| UI 나무판 | *미정* |
| UI 한지 (패널 안쪽) | *미정* |
| 윤곽선 검정 | *미정* |
| 지원 주민 테두리 | *미정* |

## 5. 선과 면

- 윤곽선은 **굵고 검고 깔끔한 한 획**으로 긋는다.
- 선을 여러 번 겹쳐 긋거나 스케치처럼 흐트러뜨리지 않는다. **잔선 금지.**
- 면 안쪽은 단색에 가깝게 채운다. **질감·해칭·노이즈를 넣지 않는다.**
- 명암은 그라데이션 없이 **2~3단계의 면**으로만 나눈다.
- 종이 질감은 **배경 이미지에만** 아주 약하게. 캐릭터·아이콘·UI에는 넣지 않는다.

## 6. 형태 — 장난감처럼

**실사체는 절대 쓰지 않는다.** 목표는 비닐 피규어나 나무 인형에 가까운 인상이다.

- 형태를 **단순한 덩어리**로 정리한다. 구, 원통, 타원의 조합.
- 머리·몸통·팔·다리·모자·도구가 각각 **분명히 나뉜 덩어리**로 읽힌다.
- 표면은 매끈하다. 주름, 근육, 솜털, 혈관 같은 실사 디테일을 넣지 않는다.
- 손가락을 따로 그리지 않는다. 벙어리장갑처럼 뭉뚱그린다.
- 눈은 단순한 점이나 타원. 눈동자 하이라이트를 여러 겹 넣지 않는다.
- 옷 주름은 두세 줄로 끝낸다.

## 7. 비율과 크기

승인된 `player_base_stats.csv`의 `collision_radius`가 **20**이고,
`DEC-ART-001`이 논리 월드 1단위 = 화면 1픽셀로 확정했다.

**`collision_radius`는 키가 아니라 몸통 폭이다.** 화면에서 지름 40px 안팎의 원이며
캐릭터가 서 있는 자리의 굵기다. 스프라이트 높이는 이 값이 정하지 않는다.

| | 값 |
|---|---|
| 몸통 폭 | **40px 안팎** — `collision_radius` 20에서 나온다. 바꾸지 않는다 |
| 스프라이트 높이 | **100~130px** (2026-08-05) |

높이를 60~70px로 잡았다가 올렸다. 경작지 스프라이트가 157px인데 캐릭터가 그 절반도 안 되면
밭에 서 있는 사람으로 읽히지 않는다. A1 목업의 농부도 실제로는 경작지 높이에 가깝게 나왔다.

**승인 데이터는 고치지 않는다.** 키가 커져도 몸통 폭이 그대로면 판정과 그림이 어긋나지 않는다.
2.5등신에서 높이 130px이면 몸통 폭이 45~55px이라 40px 판정 원과 거의 맞는다.

| 용도 | 등신 |
|---|---|
| 컨셉아트 시트 (원본) | 4~5등신 |
| 필드 스프라이트 (SD) | 2~2.5등신 |
| 상반신 일러스트 | 대화 화면용. 가슴 위까지. 화면 높이의 절반쯤을 차지한다 |

필드에서 실사 비율로 그리면 이 크기에서 얼굴이 8px이 되어 주민 넷을 구분할 수 없다.
팔다리를 몸통에서 떼어 그려 **실루엣이 뭉치지 않게** 한다.

## 8. 도구 분담

| 도구 | 담당 |
|---|---|
| **NovelAI** | 사람 형태 — 플레이어, 주민 4명. 컨셉아트 시트 · 필드 스프라이트 · 초상화 |
| **GPT Image** | 그 외 전부 — UI, 경작지, 작물, 배경, 야생동물, 투척물, 아이콘, 컷신 |

같은 대상을 두 도구로 중복해서 뽑지 않는다.
야생동물과 작물을 GPT로 보내는 이유는 NovelAI가 인물에 특화돼 있어서다.

## 9. 제작 순서

**UI를 전부 끝낸 뒤 캐릭터로 넘어간다.**

| 단계 | 무엇 | 도구 | 장수 |
|---|---|---|---|
| **A** | **목업 4장** — 낮 필드 · 밤 필드(습격) · 정비 허브 · 대화 | GPT | 4 |
| **B** | 목업을 참조로 UI 부품 개별 생성 | GPT | 약 14 |
| **C** | 아이콘 — 작물 4 · 재료 3 · 투척무기 4 · 회복 3 · 속성 4 | GPT | 18 |
| **D** | 맵 배경 · 빈 경작지 · 씨앗 · 성장 중 4 · 수확 가능 4 | GPT | 11 |
| **E** | 야생동물 3 · 투척물 5 · 이펙트 2 | GPT | 10 |
| **F** | 캐릭터 — 플레이어와 주민 4명. 컨셉아트 시트 → 필드 스프라이트 · 초상화 | NovelAI | — |
| **G** | 엔딩 컷신 | GPT | 6 |

**A가 끝나야 B가 의미 있다.** 목업이 그대로 UI 명세가 되므로(10절) 배치를 여기서
확정하지 않으면 부품을 다 만든 뒤에 다시 배치를 고민하게 된다.
정비 허브와 대화 화면은 버튼·팝업·초상화가 몰려 있어 목업 없이 부품부터 만들면 안 된다.

**목업은 새 부품이나 새 배치가 나오는 화면만 뽑는다.** `DEC-UI-014`의 화면은 13개지만
나머지 아홉은 패널·버튼·배경의 조합이라 B단계 부품으로 조립된다.
투항 대화는 `DEC-UI-010`이 전투 전 대화와 같은 규칙으로 확정해 A4가 덮는다.

다만 `DEC-UI-023`이 조우 결과·밤 결과·런 실패·엔딩 네 화면을
*"공유 템플릿으로 묶지 않는다"* 로 확정했으므로, **D단계의 화면 배경 네 장이
서로 눈에 띄게 달라야 한다.** 목업이 없다고 같은 그림을 돌려 쓰면 안 된다.

**G는 F 뒤에 둔다.** 엔딩 컷신에 주민이 나오는데, 캐릭터를 확정하기 전에 그리면
같은 인물이 다른 사람으로 나온다.

A1 목업에 농부가 들어가지만 **크기와 위치를 잡기 위한 임시**다.
최종 캐릭터는 F에서 NovelAI로 따로 만든다. 목업의 농부로 캐릭터를 판단하지 않는다.

## 10. UI 파이프라인

**목업이 그대로 UI 명세가 된다.** 목업에서 레이아웃을 확정하면 구현 단계에서
배치를 다시 고민할 필요가 없다.

개별 요소는 목업에서 **잘라내지 않는다.** 잘라내면 해상도가 부족하고 가장자리가
지저분하다. **목업을 참조 이미지로 넣고 다시 생성**한다.

패널 테두리는 9-slice로 늘어나야 하므로 *"빈 패널 한 장, 여백 넉넉하게"* 로
따로 뽑아 모서리를 잘라낸다 (`DEC-ART-001`).

### 시트로 묶는 규칙

**부품을 하나씩 따로 뽑지 않는다.** 낱개로 뽑으면 주변에 견줄 것이 없어 이미지 AI가
밝기·채도·디테일 양을 매번 새로 정한다. 다섯 번 뽑으면 다섯 개가 다 다르게 나온다.
**한 장 안에 여러 부품을 함께 그리면 서로 같은 결로 나온다.**

묶는 기준은 두 가지이고 **둘 다 만족해야** 한 시트다.

1. **재질이 같다** — 나무 판자끼리, 게이지끼리, 한지 패널끼리
2. **화면에 표시되는 크기대가 비슷하다** — 100px 안팎끼리, 화면 전체끼리

| 시트 | 담을 것 |
|---|---|
| HUD 나무판 | 표지판 · 플레이어 상태 카드 · 퀵슬롯 칸 · 회복 아이템 칸 · 설정 버튼 |
| 게이지 | 재배 시간 · 플레이어 체력 바 · 회복 사용 · 적대 주민 체력 |
| 패널·버튼 | 9-slice 빈 패널 · 팝업 틀 · 닫기 버튼 · 버튼 기본·눌림·비활성 |
| 경작지와 작물 | 빈 경작지 · 씨앗 · 작물 4종 × 성장 중·수확 가능 |
| 아이콘 | C단계 18개 |
| 야생동물 | 3종 |
| 투척물·이펙트 | 투척물 5 · 이펙트 2 |

**화면 전체를 덮는 것은 절대 시트에 넣지 않는다. 한 장에 하나씩 단독으로 뽑는다.**

- 밭 바닥 배경
- 수풀 테두리 앞 겹
- 정비 셔터
- 화면 배경 9장
- 타이틀 로고
- 엔딩 컷신 6장

이것들을 작은 부품과 같은 시트에 넣으면 **시트 비율이 정사각형으로 찌그러지고 화면
전체 에셋이 1920×1080 비율을 잃는다.** 크기대가 다른 것을 섞으면 생기는 일이다.

### 시트를 뽑을 때 프롬프트에 넣을 것

```
아래 부품들을 한 장에 함께 그린다. 서로 겹치지 않게 넉넉히 띄워 배치한다.
배경은 단색 한 가지로 둔다. 그림자를 배경에 떨어뜨리지 않는다.
각 부품은 실제 게임에서 가로 100픽셀 안팎으로 표시된다.
그 크기에서 읽히도록 단순하게 그린다. 작은 무늬와 잔 그림자를 넣지 않는다.
시트의 가로세로 비율을 맞추려고 부품 크기나 배치를 왜곡하지 않는다.
```

**UI를 뽑을 때는 12.1 고정 블록에서 `[세계관]`과 `[형태]`를 뺀다.**
`[형태]`의 *"비닐 인형이나 나무 장난감 같은 인상"* 은 캐릭터용이라 UI에 걸리면
나무 판자가 둥글둥글해진다. `[레퍼런스]` `[선과 면]` `[색]` 에 12.5를 붙인다.

### 게이지는 한 장이다

게이지는 두 부분이지만 **그림은 한 장뿐이다.**

| 부분 | 무엇 | 어디서 |
|---|---|---|
| 안 움직이는 것 | 나무 테두리 **와 빈 홈** | 스프라이트 한 장 |
| 움직이는 것 | 채워지는 면 | `src/ui/layout.css`의 색 |

`DEC-ART-001`이 *"색·여백·그림자·글로우는 `src/ui/layout.css`의 값으로 관리하고
**이미지로 만들지 않는다**"* 로 확정했다. 채움은 코드가 그리는 단색 면이다.

**테두리와 홈 바닥을 두 장으로 나누지 않는다.** 둘 다 정지해 있고 사이에 아무것도
들어가지 않는다. 채움은 홈 **위에** 그린다.

대신 **홈의 안쪽 여백을 알려줘야** 코드가 채움을 정확히 그린다. 게이지를 뽑을 때
사방 여백을 균일하게 만들면 값이 하나로 끝난다.

| 파일 | 캔버스 | 홈 안쪽 여백 (좌·우·상·하) |
|---|---|---|
| `heal_gauge` | 38×139 | 12 · 12 · 12 · 12 |
| `farming_timer` | 911×83 | 약 51 · 73 · 24 · 23 — **좌우가 22px 어긋난다** |

`farming_timer`는 채움이 오른쪽 끝에서 남거나 넘친다. 좌우를 맞추거나 두 값을 따로
넘겨야 한다.

**적대 주민 체력 게이지는 회복 사용 게이지를 90° 돌려 쓴다.** 한 파일이므로 논리 에셋 ID도
하나다. 회전은 코드가 그릴 때의 변환이지 별도 그림이 아니다. 습격 중에 둘이 동시에 뜨지만
하나는 플레이어 옆 세로, 하나는 주민 위 가로라 방향과 자리로 구분된다.
다만 38px 두께는 스프라이트 높이에 견줘 두꺼우므로 그릴 때 60% 안팎으로 줄인다.

### 목업은 배치의 기준이지 질감의 기준이 아니다

**부품을 뽑을 때 목업을 질감 기준으로 삼지 않는다.** 목업은 몇 번씩 고쳐 쓰는데,
`precise-object-edit`은 "이 부분만 바꿔라"라고 해도 전체를 다시 인코딩해서 유지하라고 한
영역까지 미세하게 다시 그려진다. 여섯 번쯤 거치면 면 안쪽에 잔 무늬와 얼룩이 눈에 보일
만큼 쌓인다. 5절의 *"면 안쪽은 단색에 가깝게 채운다. 질감·해칭·노이즈를 넣지 않는다"* 와
정면으로 부딪힌다.

목업은 한 장이지만 부품은 화면 어디에나 깔린다. **그래서 목업보다 부품이 더 깨끗해야 한다.**

참조 이미지를 둘로 나누어 역할을 명시한다.

| 무엇을 | 어디서 |
|---|---|
| 배치·형태·구조 | 그 화면의 최신 목업 |
| **질감·선 굵기·나무 톤·명암 단계** | **기준본** |

**기준본은 편집을 가장 적게 거친 깨끗한 산출물이다.** 2026-08-06 기준으로는
`assets/source/phase-b/sheets/a1_hud_components_sheet_chroma.png`다. A1-v5에서 한 번에
생성해 누적이 없고, 거기서 나온 9종이 이미 `assets/final/`에 확정돼 화면에서 쓰이고 있다.
**이미 쓰고 있는 나무가 그것**이므로 새 부품이 여기 맞아야 화면이 갈리지 않는다.

기준본은 더 깨끗한 것이 나오면 바꾼다. 바꿀 때 이 문단에 적는다.

프롬프트에 아래를 그대로 넣는다.

```
[참조 이미지의 역할]
이미지 1(최신 목업)은 배치와 형태만 참조한다. 어떤 부품이 있고 어떻게 생겼는지만 본다.
이미지 2(기준본 시트)는 질감과 선의 기준이다. 나무 색, 선 굵기, 명암 단계,
면 안쪽의 깨끗함을 여기에 맞춘다.

[질감]
이미지 1은 여러 번 편집을 거치며 면 안쪽에 잔 무늬와 얼룩이 쌓였다.
그것을 따라 그리지 않는다. 면 안쪽을 단색에 가깝게 새로 칠한다.
나뭇결은 굵은 획 두세 개로 끝내고 잔 결을 촘촘히 넣지 않는다.
얼룩, 반점, 종이 구김, 물결지는 무늬를 넣지 않는다.
명암은 그라데이션 없이 두세 단계의 면으로만 나눈다.
```

## 11. 캐릭터 파이프라인

캐릭터 하나마다 **컨셉아트 시트를 먼저 만든다.** 정면·측면·후면 전신과 얼굴
확대샷, 표정 몇 가지가 한 장에 들어간 흔한 형식이다.

그 뒤 자세·표정·SD 변형이 필요할 때마다 **그 시트를 참조 이미지로 넣어** 뽑는다.
시트 없이 매번 새로 뽑으면 같은 주민이 세션마다 다른 사람이 된다.

```
컨셉아트 시트 1장  →  필드 SD 스프라이트  (2~2.5등신 변형)
                   →  상반신 일러스트     (대화 화면 · 조우 결과 공용)
                   →  자세·표정 변형
```

**상반신 일러스트 한 장을 두 곳에서 쓴다.** 대화 화면(A4)과 조우 결과 화면
(`DEC-UI-011`의 초상화 틀)이 같은 그림을 쓴다. 따로 만들면 같은 사람이 두 얼굴이 되고,
`content_assets.csv`의 고유키가 (콘텐츠, 역할)이라 한 주민에 `portrait` 역할은 하나뿐이다.

**플레이어도 상반신 일러스트가 필요하다.** 대화 화면 오른쪽에 선다.

### 기능 선택

| 하고 싶은 것 | 쓸 기능 |
|---|---|
| 같은 인물, 다른 포즈 | **Vibe Transfer** / Character Reference |
| 표정만 바꾸기 | Director Tools 감정 변경, 또는 인페인트 |
| 2등신 SD 변형 | Vibe Transfer + `chibi` 태그 |
| 구도는 그대로 두고 살짝 손보기 | img2img (강도 낮게) |
| 누끼 | Director Tools 배경 제거 |

**img2img가 아니라 Vibe Transfer가 기본이다.** img2img는 원본 구도를 붙들고 있어서
포즈를 크게 바꾸면 뭉개진다. Vibe Transfer는 참조 이미지에서 인물의 생김새와 화풍만
가져오고 포즈는 새 프롬프트가 정한다.

### 주의

- **시트를 통째로 참조에 넣지 않는다.** 정면·측면·후면이 한 장에 있어서 모델이
  여러 명이 있는 그림으로 읽고, 결과에 사람이 둘셋 나온다.
  **시트에서 정면 전신 한 컷만 잘라내** 참조로 쓴다.
- **4~5등신 → 2등신 변형은 한 번에 안 나온다.** 얼굴·색·옷은 따라오지만 비율은
  프롬프트가 결정하는 영역이라, 참조 강도를 올리면 등신이 안 줄고 내리면 인물이
  달라진다. 몇 번 돌려 중간값을 찾는다.

시트와 잘라낸 정면 컷은 `assets/source/`에 남긴다. 게임에는 안 들어가지만
**다음에 같은 캐릭터를 뽑을 때 반드시 필요하다.**

### 12.2 GPT — A단계 목업 4장

네 장 모두 고정 블록(12.1) 뒤에 이어 붙인다. **한 번에 한 장씩** 뽑는다.

목업은 배치를 확정하는 것이 목적이므로 **1920×1080 비율**로 뽑는다 (`DEC-ART-001`).

**`(위치)`는 비워둔 채로 GPT에 넣지 않는다.** 확정 DEC는 UI 요소의 목록과 서로 간의
상대 위치만 정했고 화면 어느 구석인지는 정하지 않았다. 빈칸으로 넣으면 GPT가 임의로
정하고, 목업이 그대로 UI 명세가 되므로(10절) 그 임의값이 그대로 굳는다.
손스케치로 채운 뒤 넣는다.

공통으로 덧붙일 것:

```
[출력]
1920x1080 비율의 게임 화면 한 장.
화면에 실제로 들어갈 UI를 배치까지 포함해 그린다.
글자를 넣지 않는다. 문구 자리는 빈 면으로 두거나 알아볼 수 없는 흐린 획으로 대신한다.
```

**A2와 A4는 A1이 확정된 뒤에 뽑는다.** 셋 다 같은 필드 위에 놓이므로 A1에서 정한
밭 크기와 HUD 자리를 그대로 물려받아야 한다. A1을 참조 이미지로 함께 넣는다.

**A1 — 낮 플레이 화면 (재배 모드)**

**필드는 화면을 꽉 채우지 않는다.** 승인된 `maps.csv`의 월드가 1600×900이고
`DEC-ART-001`이 월드 1단위 = 화면 1픽셀로 확정했으므로, 1920×1080 화면 정중앙에
1600×900 필드가 놓이고 **좌우 160px · 상하 90px의 띠가 남는다.**
`src/render/camera.ts`가 *"남는 영역은 여백이 되어 필드 HUD가 쓴다"* 로 적어둔 그 띠다.

필드 안의 좌표는 이미 승인 데이터가 정했다. 화면 좌표는 월드 좌표에 (+160, +90)이다.

| 대상 | 월드 | 화면 |
|---|---|---|
| 경작지 6칸 (3열×2행) | x 660·800·940 / y 480·600 | x 820·960·1100 / y 570·690 |
| 농부 재배 시작 위치 | (800, 420) | (960, 510) |
| 야생동물 출현점 8개 | 전부 가장자리 | — |

**밭 바깥 띠는 숲이다.** 검은 여백으로 두면 "화면 밖"으로 읽혀서 야생동물이 아무 데서나
튀어나오는 것처럼 보인다. 띠를 수풀로 채우면 세계가 이어지는 곳이 되고 동물이 어디서
왔는지가 설명된다. 밭 윤곽도 직사각형이 아니라 수풀 라인을 따라 울퉁불퉁하다.

수풀은 **두 겹**이다. 앞 겹이 없으면 동물이 수풀 앞에 나타나 여전히 튀어나오는 것처럼
보인다. 밑에서 나오는 인상은 앞 겹이 만든다.

| 겹 | 범위 | 그리는 순서 | 에셋 |
|---|---|---|---|
| 뒤 겹 | 밭 바깥 영역 전체 | 동물보다 뒤 | **밭 바닥과 한 장** — `asset.background.prototype_field` |
| 앞 겹 | 밭 안쪽 가장자리 60~80px에 걸치는 잎사귀 | 동물보다 **앞** | `asset.ui.field_frame_front` |

**뒤 겹을 밭 바닥과 나누지 않는다.** 2026-08-05에 두 장으로 뽑아 보니 둘 다 1920×1080
전면 불투명이라 겹치면 하나가 다른 하나를 완전히 가렸다. 나눌 이유가 애초에 없었다 —
둘 사이에 그려지는 것이 아무것도 없다. 야생동물 출현점도 밭 안쪽 80px이라 뒤 겹 위로
오지 않는다.

배경 한 장은 **1920×1080**이며 화면 중앙에 맞춰 그린다. 월드는 1600×900이지만 배경은
밭 바깥까지 포함하므로 월드 크기와 같지 않다.

**승인된 출현점을 고치지 않는다.** `wildlife_spawn_edge_margin`이 80이고 출현점 여덟 개가
전부 밭 가장자리에서 80px 안쪽이라, 앞 겹을 60~80px로 두면 출현점이 잎사귀 선에 정확히
놓인다. 동물이 수풀에 반쯤 가려진 채 나타나 걸어 나온다.
적대 주민 출현점 (800, 100)도 잎사귀 선 안쪽이라 **주민이 숲에서 걸어 나오는 연출**이
따로 만들지 않아도 생긴다.

**앞 겹은 성글게 한다.** 잎사귀가 빽빽하면 밭 가장자리에 선 플레이어가 가려져 3절의 판독
우선 원칙에 걸린다. 잎 사이로 실루엣이 비치는 정도가 안전하다. 경작지는 전부 밭 중앙이라
실제 플레이 영역은 가려지지 않는다.

**A2 — 밤 필드 (습격 모드)**

**A3 — 정비 허브**

**2026-08-05에 구현 화면 캡처를 받아 배치를 확정했다** (`docs/planning/captures/`).
아래는 그 배치를 옮긴 것이다. **캡처의 크기는 반영하지 않는다** — 캡처의 패널과 버튼은
전부 작고 특히 보관함이 좁다. 위치와 순서만 가져오고 크기는 목업이 새로 정한다.

**팝업을 연 상태로 뽑는다.** 팝업이 닫힌 화면은 가운데가 비어 목업의 값이 없다.
제작 팝업이 가장 정보가 많으므로 그것을 연다. 팝업 안쪽은 **목록 왼쪽 · 상세 오른쪽**의
2단 구조이며 판매·구매·편성 팝업도 같은 구조를 쓴다. 그래서 팝업 목업은 이 하나로 족하다.
그 구조로 담기지 않는 팝업이 드러나면 그때 목업을 하나 더 만든다.

```
[화면]
창호지를 바른 미닫이문 두 짝이 가운데서 맞닿아 화면 전체를 덮고 있다.
밭은 조금도 보이지 않는다. 왼쪽 문과 오른쪽 문이 화면 정중앙에서 만나며
맞닿은 자리에 세로선 하나가 지난다.
문은 가는 나무 살이 격자로 짜여 있고 그 위에 한지가 발려 있다.
바깥에서 빛이 들어와 한지가 은은하게 밝다. 살의 그림자가 한지에 비친다.
이 문이 화면의 배경이며 그 앞에 정비 화면이 놓인다.

[배치]
화면 왼쪽 — 세로로 긴 보관함 패널 하나. 화면 높이를 거의 다 쓰고 폭은 화면의 약 4분의 1이다.
  패널 맨 위에 소지금 한 줄. 왼쪽에 이름 자리, 오른쪽 끝에 숫자 자리.
  그 아래 가로 구분선 하나.
  구분선 아래로 묶음 네 개가 세로로 이어진다. 순서대로 수확물, 재료, 무기, 소모품이다.
  각 묶음은 작은 제목 한 줄과 그 아래 항목 줄들로 이루어진다.
  항목 한 줄은 왼쪽에 정사각형 아이콘, 그 옆에 이름 자리, 오른쪽 끝에 수량 자리다.
  수확물 묶음에 항목 세 줄, 재료 묶음에 두 줄, 무기 묶음에 네 줄을 그린다.
  소모품 묶음은 항목이 없어 짧은 한 줄만 차지한다.
  아이콘은 작물, 자루와 병, 던지는 무기처럼 서로 다른 것으로 그린다.
화면 위쪽, 보관함 오른쪽 — 화면 제목이 들어갈 가로로 긴 빈 면 하나.
  그 오른쪽에 작은 표지 하나. 오늘 밤의 습격 예고다. 짧은 표지이며 긴 문장이 아니다.
그 아래 — 가로로 나란한 버튼 네 개. 폭이 서로 같고 남은 가로를 고르게 나눈다.
화면 오른쪽 위 구석 — 톱니바퀴 버튼 하나.
화면 오른쪽 아래 구석 — 가로로 긴 버튼 하나. 정비를 끝내는 버튼이다.

화면 가운데 — 팝업 하나가 열려 있다. 왼쪽 보관함 패널과 소지금을 가리지 않는다.
  팝업 오른쪽 위 모서리에 닫기 버튼 하나.
  팝업 안은 세로 선 하나로 왼쪽과 오른쪽이 나뉜다.
  왼쪽은 목록이다. 위아래로 묶음 두 개가 있다.
    위 묶음에 항목 네 줄, 아래 묶음에 항목 세 줄.
    항목 한 줄은 정사각형 아이콘과 이름 자리로 이루어진다.
    맨 아래 항목 하나만 흐리게 처리해 아직 열리지 않은 것으로 보이게 한다.
    위에서 두 번째 항목은 지금 고른 것이라 밝게 강조한다.
  오른쪽은 고른 항목의 상세다. 위에서 아래로 이렇게 쌓인다.
    큰 정사각형 아이콘 하나와 그 옆의 이름 자리
```

```
[담을 것 — 한 장에 함께, 서로 넉넉히 띄워서]

1. 빈 패널 틀 하나
   가로세로 비율이 정사각형에 가깝다. 세로로 긴 패널이 아니다.
   테두리만 있고 안쪽은 완전히 비어 있다. 안쪽에 아무 무늬도 넣지 않는다.

   모서리에서 변으로 넘어가는 지점이 눈에 분명하게 보인다.

   정사각형. 상하좌우로 이어 붙여도 이음매가 보이지 않아야 한다.

   작은 정사각형 나무 판자에 X 모양이 새겨져 있다.

[출력]
```

**패널을 정사각형에 가깝게 요구하는 이유**는 9-slice로 자를 때 위아래 변과 좌우 변이
모두 충분히 보여야 하기 때문이다. 목업의 패널은 세로로 길어 가로 변이 짧다.

**나오면 확인할 다섯**

- 패널 안쪽이 비어 있는가. 목록이나 칸이 그려져 있으면 다시 뽑는다
- 네 모서리가 같은가. 하나만 달라도 9-slice에서 티가 난다
- 한지 조각이 이어 붙는가. 가장자리에 그라데이션이나 그림자가 있으면 격자무늬가 생긴다
- 버튼 셋의 크기가 같은가. 하나만 커도 눌렀을 때 튄다

**코드는 고정 크기로만 쓴다.** 2026-08-06에 플레이 중 패널 크기가 변하지 않게 하기로

뿐이고, 폭이 네 가지(340·560·620·760)라 한 장으로 넷을 덮는 이득은 그대로다.

## 13. 후처리와 기록

### 13.1 역할 분담 — 이미지 AI는 그림만 만든다

**이미지 AI는 저장소에 파일을 쓰지 않는다.** 누끼, 시트 분리, 파일 이름 짓기,
`assets/final/`에 넣기는 전부 사람이 한다.

| 하는 일 | 누가 |
|---|---|
| 시트·목업 생성 | 이미지 AI |
| 시트에서 부품 분리 | 사람 (Figma) |
| 배경 투명화 | 사람 (Figma) |
| 파일 이름 짓기 | 사람. 13.2절 규칙 |
| `assets/final/`에 넣기 | 사람 |
| `CREDITS.md` 기록 | 사람. 이미지 AI에게 초안을 받아도 검토는 사람 |

이미지 AI에게 저장소 쓰기를 맡기면 이름 규칙을 지키지 않고, 누끼 품질을 확인할 수
없으며, 되돌리는 데 만드는 것보다 오래 걸린다. **프롬프트에 아래를 넣는다.**

```
[하지 않을 것]
파일을 저장하거나 폴더에 넣지 않는다. 이름을 짓지 않는다.
배경을 투명하게 만들지 않는다. 단색 배경 그대로 둔다.
시트를 잘라 개별 파일로 나누지 않는다.
결과는 이미지 한 장으로만 준다.
```

### 13.2 파일 이름

`DEC-ART-001`이 논리 에셋 ID를 `asset.<구간>.<이름>`으로 확정했고, 경로는
**카탈로그 없이 규칙으로 해석**한다.

```
asset.<구간>.<이름>   →   assets/final/<구간>/<이름>.<확장자>
```

**폴더가 곧 구간이다.** 파일 이름은 마지막 마디만 쓴다. 영문 소문자·숫자·밑줄만
사용하고 한글·공백·대문자·날짜·버전 번호를 넣지 않는다.

A1에서 나온 것들의 확정 이름이다.

| 파일 | 논리 에셋 ID |
|---|---|
| `assets/final/background/prototype_field.png` | `asset.background.prototype_field` |
| `assets/final/ui/field_frame_front.png` | `asset.ui.field_frame_front` |

### 14.5 바나나를 대체할 작물 — 아트보다 데이터가 먼저다

2026-08-05에 바나나를 토란으로 바꾸기로 이야기했다. **아직 승인 데이터에 반영되지
않았고, 아트 파일 이름을 여기에 맞춰 먼저 지으면 안 된다.**

`crop.banana`는 승인 CSV **여덟 개**에 걸쳐 있다.

```
crops.csv               crop.banana 행
crop_attributes.csv     미끄러움의 design_intent "바나나 전용"
crafting_materials.csv  천 자루·꿀의 design_intent
crop_mastery_unlocks.csv
recipes.csv             recipe.banana_peel · recipe.honey_banana · recipe.fruit_honey_bowl
recipe_inputs.csv       3행
recovery_items.csv      recovery_item.honey_banana · fruit_honey_bowl 의 설명문
throwable_weapons.csv   throwable_weapon.banana_peel
wildlife.csv            까마귀의 design_intent "카운터: 바나나 껍질"
```

**ID를 바꿀지 표시 이름만 바꿀지를 먼저 정해야 한다.**

| | 하는 일 | 위험 |
|---|---|---|
| 표시 이름만 | `display_name`·설명문·`design_intent`만 수정 | 낮다. 참조 무결성이 안 깨진다 |
| ID까지 | 여덟 파일의 참조를 동시에 수정 | 하나라도 놓치면 검증이 차단된다 |

내부 ID는 플레이어에게 보이지 않으므로 **표시 이름만 바꾸는 쪽**을 권한다. 다만
`recipe.banana_peel` 같은 ID가 남아 다음 사람이 헷갈릴 수 있다.

**속성은 유지된다.** 토란은 점액질이라 `crop_attribute.slippery`가 그대로 성립한다.
다만 "바나나 껍질을 밟으면 미끄러진다"는 만화적 관습이 토란에는 없으므로,
투척 무기의 표시 이름과 설명문을 콘텐츠 담당자가 다시 써야 한다.

**아트 파일 이름은 `crops.csv`가 정리된 뒤 붙인다.** 그림은 지금 뽑아도 되지만
`assets/source/`에만 두고 `assets/final/`로 옮기지 않는다. 에셋 이름이 작물 ID와
같을 필요는 없다 — 그 연결이 `content_assets.csv`가 존재하는 이유다. 그림이 토란이면
에셋 이름도 토란으로 짓고, 작물 ID는 그대로 두어도 규칙에 어긋나지 않는다.

### 14.6 A1 산출물 검수에서 나온 것 (2026-08-05)

**HUD는 밭 바깥 띠를 넘어 밭 위로 올라온다.** 의도한 것이다.

띠는 위아래 각 90px인데 부품이 그보다 크다 — 상태 카드 200, 회복 칸 191, 표지판 166,
퀵슬롯 161, 설정 버튼 114. 화면 네 모서리는 수풀이라 시각적으로는 자연스럽지만,
**논리 필드는 여전히 1600×900 전체**이므로 플레이어가 화면 구석까지 걸어가면 HUD 뒤에
가린다. 경작지가 전부 밭 중앙이라 실제 플레이에서는 드물다.

**경작지 간격을 넓힌다.** 스프라이트가 174×157인데 승인된 간격이 140×120이라 인접 칸이
가로 34px·세로 37px씩 겹친다. 스프라이트를 줄이는 대신 간격을 넓히기로 했다 — 줄이면
경작지가 화면에서 너무 작아진다.

```
현재   x 660 · 800 · 940      y 480 · 600
변경   x 600 · 800 · 1000     y 435 · 615
```

간격이 200×180이 되어 칸 사이에 가로 26px·세로 23px의 틈이 생긴다. 확인한 것은 다음과
같다. 격자 전체가 x 513~1087, y 356~693에 들어가 수풀 안쪽 경계(가장자리 80px)와 넉넉히
떨어진다. `ally_support`(560, 700)는 좌하단 경작지 바깥에 남는다. `player_farming_start`와
`player_raid_start`가 경작지와 겹치는 것은 지금과 같고 새로 생기는 문제가 아니다.
이동속도 260이라 칸 사이 이동이 0.54초에서 0.77초로 늘지만 재배 제한시간 60초에 견주면
차이가 작다. `tests/`는 합성 좌표를 쓰므로 영향이 없다.

`farm_plots.csv`는 승인 데이터이므로 **콘텐츠 담당자가 고친다.** 공통 열이 없는 연결
테이블이라 `content_version`은 없고 좌표만 바꾼 뒤 `data:validate`를 다시 돌리면 된다.

### 14.7 플레이어 에셋을 연결할 자리가 없다 (2026-08-05)

**문제 유형: 규칙 누락.** 대화 화면에 플레이어 상반신 일러스트를 넣기로 하면서 드러났다.

`content_assets.csv`의 부모 후보는 아래 아홉 테이블이다.

```
maps · crops · crafting_materials · throwable_weapons · recovery_items
wildlife · wildlife_spawn_profiles · residents · endings
```

**`player_base_stats.csv`가 없다.** 그래서 플레이어의 필드 스프라이트와 상반신 일러스트를
어느 콘텐츠 행에도 붙일 수 없다. `schema/enums.json`의 UI·시스템 고정 목록도 답이 아니다 —
`DEC-ART-001`이 그 목록의 범주를 화면 배경·로고·셔터·패널·버튼·UI 아이콘·HUD 틀·폰트로
한정했고 구간도 `ui`, `logo`, `hud`, `font`뿐이라 인물 그림이 들어갈 자리가 아니다.

A1 목업의 농부는 임시라 지금까지 걸리지 않았지만, F단계에서 실제 플레이어 캐릭터를 만들면
바로 막힌다.

**추천안** — `content_assets.csv`의 부모 후보에 `player_base_stats.csv`를 더한다.
승인 행이 정확히 하나라 참조가 모호해지지 않고, `asset_role`의 `field_sprite`와 `portrait`를
그대로 쓸 수 있다. `DEC-ART-001`은 역할 목록만 확정했고 어떤 테이블이 어떤 역할을 가질 수
있는지는 정하지 않았으므로(`content_assets.json`의 주석) **DEC 변경 없이 스키마 수정으로
끝난다.** 스키마 담당에게 넘긴다.

**임시로 우회하지 않는다.** 플레이어 그림을 `asset.ui.*`로 만들거나 주민 행에 끼워 넣으면
고정 목록의 의미가 무너진다.
