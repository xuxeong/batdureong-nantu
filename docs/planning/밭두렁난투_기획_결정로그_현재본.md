**밭두렁난투 기획 결정 로그**

이 문서는 기획 대화 중 확정·보류·폐기된 결정을 누락 없이 추적하기 위한 작업용 기록이다.
최종 저장소 문서는 이 로그의 `확정` 항목을 기준으로 작성한다.

이 문서는 처음부터 끝까지 읽는 설명서가 아니라 결정의 근거와 상태를 확인하는 원장이다.
게임을 처음 이해하려는 팀원은 `밭두렁난투_시스템_UIUX_기획서_현재본.md`를 먼저 읽고, 콘텐츠 작업을 시작하려는 팀원은 `밭두렁난투_콘텐츠_데이터_준비도_점검.md`를 함께 사용한다.

문서별 역할:

| 문서 | 역할 | 주 독자 |
|---|---|---|
| `AGENTS.md` | 모든 AI가 먼저 적용할 역할, 문서 권한, 승인 절차와 변경 안전 규칙 | 모든 팀원, 모든 작업 AI |
| `밭두렁난투_시스템_UIUX_기획서_현재본.md` | 현재 게임의 구조와 플레이 흐름을 설명하는 읽기용 기획서 | 모든 팀원, 구현 AI |
| `밭두렁난투_기획_결정로그_현재본.md` | 확정·보류·폐기 결정의 원문과 ID를 보존하는 기준 원장 | 기획 책임자, 검증 AI |
| `밭두렁난투_콘텐츠_데이터_준비도_점검.md` | 콘텐츠 담당자가 데이터 틀부터 값 작성까지 진행하는 순서와 AI 프롬프트를 제공하는 작업 가이드 | 콘텐츠·레벨 담당자, 콘텐츠 제작 AI |

상태 읽는 법:

- `확정`: 현재 구현과 콘텐츠가 반드시 따라야 하는 규칙이다.
- `보류`: 아직 정하지 않았으며 재검토 조건이 충족되기 전에는 AI가 임의로 채우면 안 된다.
- `폐기`: 과거 기록이다. 현재 규칙으로 사용하지 않고 `대체 결정`을 따른다.

AI가 이 문서를 사용할 때 지킬 규칙:

1. 폐기되지 않은 `확정` DEC만 현재 규칙으로 사용한다.
2. `보류` DEC를 확정 사실처럼 가정하지 않는다.
3. 제안이 확정 DEC와 충돌하면 몰래 수정하지 말고 충돌 ID, 이유, 대안을 먼저 보고한다.
4. 콘텐츠 값을 제안할 때 관련 DEC와 데이터 템플릿 ID를 함께 적는다.
5. 사실, 가정, 제안, 사용자 확인이 필요한 항목을 구분한다.
6. 승인 전 결과는 초안이며 승인 콘텐츠와 런타임 데이터를 직접 덮어쓰지 않는다.
7. 한 번에 한 콘텐츠 분야만 다루고 검증을 마친 뒤 다음 분야로 이동한다.

- 제목 1은 `런 구조와 단계 전환`과 같은 기획 대분류에만 사용한다.
- 제목 2는 `DEC-...`로 시작하는 개별 결정에만 사용한다.
- 결정 로그에는 확정, 명시적 보류, 과거에 확정됐다가 폐기된 결정만 기록한다.
- 확정 전 검토 과정에서 채택되지 않은 제안은 기록하지 않는다.
- ID에는 상태를 넣지 않으며 한 번 발급한 ID는 변경하거나 재사용하지 않는다.
- 확정 상태의 항목은 `상태`, `결정일`, `결정`만 사용한다.
- 보류 상태의 항목은 `상태`, `재검토 조건`만 사용한다.
- 폐기 상태의 항목은 `상태`, `결정일`, `결정`, `폐기일`, `폐기 이유`, `대체 결정`만 사용한다.
- 사용자가 결정을 확정하면 작업용 로그와 사용자 공개용 현재본을 같은 응답에서 함께 갱신한다.
- 새로운 기획 대분류를 시작할 때 해당 단계와 관련된 모든 보류 DEC의 재검토 조건을 점검한다.
- 프로토타입 QA가 끝났을 때 QA 결과를 조건으로 둔 모든 보류 DEC를 점검한다.
- 프로토타입 범위 동결과 최종 기획서 작성 전에는 전체 보류 DEC를 다시 점검한다.
- 보류 DEC의 재검토 조건이 충족되면 다음 관련 기획으로 넘어가기 전에 해당 ID와 검토 필요성을 사용자에게 알린다.
- 재검토한 보류 DEC를 채택하면 같은 ID를 유지한 채 상태를 `확정`으로 바꾸고 확정 상태의 필드 구조를 적용한다.
- 재검토 후 다시 보류하면 같은 ID를 유지하고 새로운 재검토 조건으로 갱신한다.
- 한 번도 확정되지 않은 보류 DEC를 채택하지 않기로 하면 로그에서 제거하고 해당 ID는 재사용하지 않는다.
- 확정 DEC의 제목과 결정 텍스트는 기본적으로 불변으로 취급한다.
- 확정 DEC에 설명을 보강하거나 문구를 수정해야 할 때는 수정 전에 대상 ID, 수정 이유, 변경되는 내용을 사용자에게 고지한다.
- 확정 DEC의 의미가 바뀌는 경우 기존 결정을 덮어쓰지 않고 기존 DEC를 폐기한 뒤 새로운 숫자 ID의 대체 DEC를 작성한다.

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 레시피를 선택하는 것만으로는 제작이 발생하지 않는다.
  - 플레이어는 한 종류의 레시피와 1 이상의 정수 제작 횟수를 지정한다.
  - 지정한 제작 횟수에 따라 전체 필요 재료와 전체 결과 수량을 계산한다.
  - `제작` 버튼을 누르면 지정한 한 종류의 레시피 제작을 즉시 확정한다.
  - 제작 버튼을 누르는 순간 필요한 모든 재료의 현재 보유 수량을 다시 검증한다.
  - 재료가 충분하면 필요한 모든 수확물과 조합 재료를 차감하고 전체 결과물을 추가한다.
  - 재료가 부족하면 어떤 재료와 결과물도 변경하지 않는다.
  - 제작 처리 중에는 동일한 제작 버튼의 중복 입력을 차단한다.
  - 하나의 제작에서 재료 일부만 차감되거나 결과물 일부만 추가되는 상태를 허용하지 않는다.

## DEC-PIPELINE-001 — AI 콘텐츠 초안과 승인 흐름

- 상태: 폐기
- 결정일: 2026-07-31
- 결정:
  - AI 콘텐츠 제작은 `사연·성격 원본 → AI 초안 → 콘텐츠 담당자 검토 → 승인 콘텐츠 → 런타임 데이터 생성` 순서로 진행한다.
  - AI는 콘텐츠 초안만 작성할 수 있다.
  - AI가 승인 콘텐츠나 런타임 데이터를 직접 덮어쓸 수 없다.
  - 콘텐츠 담당자가 검토하고 승인 상태로 전환한 콘텐츠만 게임에서 사용한다.
  - 사연 정보, 주민 성격, 선택 기능처럼 대사 작성의 원본이 변경되면 관련 대사를 `재검토 필요` 상태로 변경한다.
  - 관련 대사를 재검토하는 동안에는 마지막 승인본을 게임에서 계속 사용한다.
- 폐기일: 2026-07-31
- 폐기 이유:
  - 승인 흐름의 입력과 재검토 대상을 사연·성격·대사로 표현해 주민 대사 외의 콘텐츠 데이터에는 적용되지 않는 규칙으로 오해할 수 있다.
- 대체 결정:
  - `DEC-PIPELINE-004`

## DEC-PIPELINE-002 — 런타임 데이터와 초안의 저장 원칙

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 런타임 데이터는 승인 콘텐츠에서 자동으로 생성한다.
  - 자동 생성된 런타임 데이터는 직접 수정하지 않는다.
  - 실패하거나 사용하지 않기로 한 AI 초안을 저장소에 계속 누적하지 않는다.
  - 저장소에는 승인된 현재본과 이를 재생성하는 데 필요한 원본 및 규칙을 유지한다.
  - 승인된 현재본의 변경과 변경 이유는 Git 커밋 이력으로 추적한다.

## DEC-PIPELINE-003 — AI 콘텐츠 파일 배치와 자동 생성 도구

- 상태: 보류
- 재검토 조건:

## DEC-PIPELINE-004 — 모든 콘텐츠 데이터의 AI 초안과 승인 흐름

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - AI를 활용하는 모든 콘텐츠 제작은 `콘텐츠 원본·제약 규칙 → AI 초안 → 담당자 검토 → 승인 콘텐츠 → 자동 검증 → 런타임 데이터 생성` 순서로 진행한다.
  - 이 흐름은 주민·사연·대사뿐 아니라 작물, 재료, 레시피, 투척 무기, 회복 아이템, 야생동물, 습격 주민, 전투 패턴, 일차·습격 구성, 보상, 엔딩과 그 밖의 구조화된 콘텐츠 데이터에 공통으로 적용한다.
  - AI는 콘텐츠 초안만 작성할 수 있다.
  - AI가 콘텐츠 원본, 승인 콘텐츠, 검증 규칙 또는 런타임 데이터를 직접 덮어쓸 수 없다.
  - 각 콘텐츠 분야의 담당자가 검토하고 승인 상태로 전환한 콘텐츠만 자동 검증과 런타임 데이터 생성의 입력으로 사용할 수 있다.
  - 승인 콘텐츠가 참조하는 원본 데이터나 제약 규칙이 변경되면 영향을 받는 콘텐츠를 `재검토 필요` 상태로 변경한다.
  - 재검토가 끝날 때까지 게임은 검증을 통과한 마지막 승인본을 계속 사용한다.
  - 콘텐츠 분야마다 데이터 형식이 달라도 초안·검토·승인·검증·생성의 상태 전환 원칙은 동일하게 적용한다.

## DEC-PIPELINE-005 — 콘텐츠 기획 착수 전 데이터 준비도 점검

- 상태: 폐기
- 결정일: 2026-07-31
- 결정:
  - 주민 대화·협상·관계 시스템 기획 완료 후 콘텐츠 데이터와 관련된 모든 보류 결정을 전수 검토했다.
  - 레시피와 주민 사연·대화는 콘텐츠를 작성할 수 있는 논리 데이터 구조와 검증 규칙이 마련되어 있다.
  - 실제 런 길이·습격 일정, 가격, 작물, 재료, 레시피, 숙련도, 주민·사연, 협상 요구, 전투 보정, 투항 기준, 보상, 지원 공격과 공포도 수치는 기존 보류 결정에서 콘텐츠 값 작성을 기다리고 있다.
  - 공통 콘텐츠 엔트리, 일차·습격 일정, 작물, 조합 재료·상점, 투척 무기, 회복 아이템, 야생동물, 주민 전투·지원 프로필, 대화 판정·전투 보정, 보상 묶음, 엔딩 정의·엔딩 기록 입력의 구체적인 데이터 템플릿이 아직 필요하다.
  - 누락된 데이터 템플릿은 `DEC-CONTENT-001`부터 `DEC-CONTENT-011`까지 보류 결정으로 등록했다.
  - UI/UX 표시 방식과 프로토타입 QA 이후 검토 항목은 콘텐츠 데이터 준비도 점검 범위에서 분리했다.
  - 콘텐츠 값을 대량 작성하기 전에 참조의 기반이 되는 공통 엔트리와 각 분야의 데이터 템플릿 및 자동 검증 규칙을 먼저 확정한다.
- 폐기일: 2026-07-31
- 폐기 이유:
  - 당시에는 유효한 준비도 점검이었지만 이후 콘텐츠 데이터 구조와 검증 규칙이 확정되어 현재 상태를 잘못 설명한다.
- 대체 결정:
  - `DEC-PIPELINE-014`

## DEC-PIPELINE-007 — AI 기반 CSV 콘텐츠 왕복 제작 흐름

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 확정된 데이터 구조를 입력으로 사용해 AI가 콘텐츠 후보를 포함한 작업용 CSV 초안을 생성한다.
  - 콘텐츠 기획자는 작업용 CSV를 엑셀에서 열어 AI가 제안한 후보 행을 삭제하거나 새 행을 추가하고 콘텐츠 값을 수정·보완한다.
  - 콘텐츠 기획자는 확정된 필수 열 이름과 표 구조를 임의로 변경하거나 삭제하지 않는다.
  - AI는 기획자가 수정한 CSV와 마지막 승인본을 비교해 추가·삭제·변경된 콘텐츠, 누락된 필수값, 수정한 메타데이터, 연결하지 못한 참조와 규칙 충돌을 변경 보고서로 작성한다.
  - AI는 기획자의 수정본을 바로 승인본으로 덮어쓰지 않고 정규화된 승인 후보 CSV와 변경 보고서를 별도로 생성한다.
  - 콘텐츠 담당자가 승인 후보와 변경 보고서를 검토하고 명시적으로 승인한 데이터만 승인 CSV로 저장한다.
  - 승인 CSV는 자동 검증을 거친 뒤 런타임 JSON 생성의 입력으로 사용한다.

## DEC-PIPELINE-008 — CSV 작성과 정규화 원칙

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 사람과 AI가 편집하는 콘텐츠 작성 원본은 엑셀에서 열 수 있는 UTF-8 CSV를 기본 형식으로 사용한다.
  - 한 행은 한 콘텐츠 엔트리를 나타낸다.
  - 열 이름은 확정된 데이터 구조와 같은 영문 `snake_case`를 사용한다.
  - 한 셀에 여러 참조 ID를 나열하지 않는다.
  - 일대다 또는 다대다 관계는 별도의 연결 CSV에서 한 행에 한 관계만 기록한다.
  - 셀 안에 실제 줄바꿈을 저장하지 않는다.
  - 엑셀에서 저장한 CSV는 승인 후보를 만들기 전에 AI 또는 자동화 도구가 인코딩, 열 이름, 필수값과 표 구조를 검사하고 정규화한다.
  - CSV 형식으로 직접 표현하기 어려운 중첩 구조는 연결 CSV로 분리하고 런타임 데이터 생성 과정에서 다시 결합한다.

## DEC-PIPELINE-009 — AI 관리 메타데이터와 승인 보호

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 신규 콘텐츠의 ID, 콘텐츠 상태, 콘텐츠 버전, 데이터 참조와 논리 에셋 ID는 확정된 데이터 구조와 기획자가 수정한 내용을 바탕으로 AI가 초안을 작성하거나 정규화한다.
  - AI가 제안한 메타데이터는 콘텐츠 담당자의 승인을 받아야 하며 AI가 승인 상태를 스스로 확정할 수 없다.
  - 신규 콘텐츠의 ID는 최초 승인 전까지 검토할 수 있고 최초 승인 후에는 표시 이름이나 내용이 바뀌어도 자동으로 변경하지 않는다.
  - 승인된 ID를 변경해야 할 때는 일반 편집이 아니라 영향을 받는 모든 참조를 확인하는 별도의 ID 이전 작업으로 처리한다.
  - 콘텐츠 버전은 마지막 승인본과 승인 후보 사이의 의미 있는 콘텐츠 변경을 기준으로 AI가 계산하고 사람의 승인 시점에 확정한다.
  - 행 정렬이나 열 순서처럼 콘텐츠 의미가 바뀌지 않은 형식 변경은 콘텐츠 버전 증가 사유로 사용하지 않는다.
  - AI가 참조 대상을 확실하게 연결할 수 없으면 임의의 ID를 만들지 않고 오류 또는 `TBD`로 보고한다.
  - 논리 에셋 ID는 실제 파일 경로와 분리하며 아트가 준비되지 않았거나 연결이 확실하지 않으면 비워 두거나 `TBD`로 보고한다.

## DEC-PIPELINE-010 — 스키마 버전과 런타임 데이터 생성

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 데이터 구조의 버전인 `schema_version`과 개별 콘텐츠 승인본의 버전인 `content_version`을 분리한다.
  - `schema_version`은 모든 콘텐츠 행에 반복하지 않고 전체 데이터 묶음의 설정에 한 번만 기록한다.
  - 필드의 추가·삭제·의미·자료형·참조 방식이 바뀌면 `schema_version`을 변경한다.
  - 스키마 버전을 변경할 때는 이전 버전, 새 버전, 변경된 구조, 기존 CSV의 변환 방법과 영향을 받는 검증·생성 과정을 기록한다.
  - 승인 CSV를 중간 데이터 객체로 변환한 뒤 확정된 스키마와 참조 규칙으로 자동 검증한다.
  - 검증을 통과한 승인 데이터만 게임이 읽는 런타임 JSON으로 생성한다.
  - 자동 생성된 런타임 JSON은 직접 수정하지 않는다.

## DEC-PIPELINE-011 — 연결 CSV의 소유권·승인·버전 규칙

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 연결 CSV 행은 독립 콘텐츠가 아니므로 공통 콘텐츠 엔트리의 ID, `content_status`와 `content_version`을 반복하지 않고 지정된 부모 콘텐츠의 승인과 버전에 귀속한다.
  - `run_schedule_days.csv`의 부모는 런 일정이다.
  - `crop_mastery_unlocks.csv`의 부모는 해금되는 레시피다.
  - `wildlife_spawn_entries.csv`의 부모는 야생동물 출현 프로필이다.
  - `personality_choice_outcomes.csv`의 부모는 주민 성격 프로필이다.
  - `dialogue_choice_responses.csv`의 부모는 대화 선택지다.
  - `reward_bundle_entries.csv`의 부모는 보상 묶음이다.
  - `ending_conditions.csv`의 부모는 엔딩이다.
  - `recipe_inputs.csv`의 부모는 레시피다.
  - `map_points.csv`와 `farm_plots.csv`의 부모는 맵이다.
  - 공통 에셋 연결 CSV의 부모는 해당 에셋을 사용하는 콘텐츠다.
  - 연결 행의 작성·검토·승인 상태는 지정된 부모 콘텐츠를 따른다.
  - 연결 행의 추가·삭제, 참조 대상 변경, 수량·조건과 그 밖의 의미 있는 값 변경은 부모 콘텐츠의 의미 있는 변경으로 처리한다.
  - 이미 승인된 연결 행을 변경하면 작업 후보의 부모 콘텐츠를 `needs_review` 상태로 표시한다.
  - 작업 후보와 별도로 마지막 승인본을 보존하며 재검토가 끝날 때까지 게임은 검증을 통과한 마지막 승인본을 계속 사용한다.
  - 변경된 연결 행과 부모 콘텐츠를 함께 승인할 때 부모의 `content_version`을 1 증가시킨다.
  - 행 정렬, 열 순서와 인코딩 정규화만 바뀐 경우에는 부모 콘텐츠 버전을 증가시키지 않는다.
  - 연결 행이 참조하는 다른 콘텐츠의 내용이 변경됐다는 이유만으로 부모 콘텐츠 버전을 자동 증가시키지 않는다.
  - 참조 대상의 ID가 이전·폐기되거나 변경된 구조와 호환되지 않으면 영향을 받는 부모 콘텐츠를 `needs_review` 대상으로 보고한다.
  - 연결 행을 포함한 부모 콘텐츠의 승인 시점에는 연결 행의 모든 참조 대상도 승인 상태여야 한다.

  - 새로운 연결 CSV를 추가할 때는 어느 참조 필드가 부모 콘텐츠를 가리키는지 스키마에 반드시 지정한다.

## DEC-PIPELINE-012 — 스키마·엔딩 프롬프트 버전의 단일 원본

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 콘텐츠 데이터 구조, 엔딩 LLM 입력 구조와 고정 엔딩 시스템 프롬프트의 버전을 콘텐츠 CSV와 분리된 단일 `schema_manifest.json`에서 관리한다.

  - `schema_version`은 전체 콘텐츠 CSV 구조와 참조 규칙의 버전이다.
  - `ending_input_schema_version`은 LLM에 전달하는 엔딩 런타임 JSON 객체 구조의 버전이다.
  - `ending_prompt_version`은 고정 엔딩 시스템 프롬프트의 버전이다.
  - 엔딩 입력과 엔딩 생성 기록의 `input_schema_version`에는 `ending_input_schema_version`을 사용한다.
  - 엔딩 입력과 엔딩 생성 기록의 `prompt_version`에는 `ending_prompt_version`을 사용한다.
  - 콘텐츠 행마다 세 버전을 반복하지 않고 생성기와 게임 코드에 같은 버전 값을 별도로 하드코딩하지 않는다.
  - 콘텐츠 필드의 추가·삭제, 자료형·의미·참조 방식 변경은 `schema_version` 증가 사유다.
  - 엔딩 입력 객체의 필드 추가·삭제, 자료형·의미 변경은 `ending_input_schema_version` 증가 사유다.
  - 고정 시스템 지시문과 출력 제약의 의미 변경은 `ending_prompt_version` 증가 사유다.
  - 개별 엔딩의 `ending_prompt_direction`을 수정하면 해당 엔딩의 `content_version`을 증가시키고 `ending_prompt_version`은 증가시키지 않는다.
  - 생성 모델 변경은 프롬프트 버전 증가 사유가 아니며 런타임 기록의 `generator_model_id`로 구분한다.
  - 공백, 정렬, 인코딩과 그 밖의 의미 없는 형식 변경은 버전 증가 사유로 사용하지 않는다.
  - 고정 시스템 프롬프트는 `ending_prompt_system.md` 한 파일을 단일 원본으로 사용하고 게임 코드에 같은 프롬프트 문장을 복사하지 않는다.
  - `ending_prompt_system.md`는 엔딩별 콘텐츠 데이터가 아니라 시스템 제약 원본으로 취급한다.
  - 명세와 프롬프트 원본의 의미 있는 변경은 영향 분석과 사람의 승인을 거치고 변경 이유를 Git 이력에 남긴다.
  - `schema_manifest.json`과 `ending_prompt_system.md`의 실제 폴더 위치는 `DEC-PIPELINE-003`의 최종 저장소 구조에서 결정한다.
  - 명세에 없는 버전으로 런타임 데이터를 생성하지 않고 엔딩 입력과 생성 기록의 버전이 명세와 일치하는지 검사한다.
  - 프롬프트 의미가 바뀌었는데 `ending_prompt_version`이 증가하지 않았으면 검토 오류로 보고한다.
  - 자동 생성 런타임 JSON과 콘텐츠 CSV는 `schema_manifest.json`과 `ending_prompt_system.md`를 덮어쓸 수 없다.

## DEC-PIPELINE-013 — CSV 값 표현과 공백 규칙

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 작업용 CSV는 엑셀 호환을 위해 UTF-8 BOM을 허용한다.
  - 승인 후보와 승인 CSV는 자동 정규화하여 UTF-8 쉼표 구분 형식으로 저장한다.
  - 헤더는 확정된 영문 `snake_case`를 사용한다.
  - 불리언은 소문자 `true`, `false`만 사용한다.
  - 정수는 단위, 천 단위 쉼표와 소수점 없이 10진수로 작성한다.
  - 실수는 마침표를 소수점으로 사용하고 `%`, 배율 단위와 초 단위를 셀에 붙이지 않는다.
  - ID·열거형·숫자 셀의 앞뒤 공백은 제거한다.
  - 표시 이름·설명·대사의 앞뒤 불필요한 공백은 제거하고 문장 내부 공백은 보존한다.
  - 선택 필드에 값이 없으면 빈 셀을 사용한다.
  - 빈 값을 `null`, `NULL`, `N/A`, `없음`, `-`로 대신하지 않는다.
  - `AUTO`와 `TBD`는 작업용 CSV와 승인 후보에서만 허용한다.
  - 승인 CSV에는 빈 필수값, `AUTO`와 `TBD`가 남아 있을 수 없다.
  - CSV 규칙에 따라 쉼표와 큰따옴표가 포함된 문장은 큰따옴표로 감싸고 내부 큰따옴표는 두 번 작성한다.
  - 셀 안의 실제 줄바꿈은 허용하지 않는다.
  - 인코딩, 줄바꿈, 따옴표와 숫자 표기 정규화만으로는 `content_version`을 증가시키지 않는다.
  - 자동 검증은 자료형과 허용 범위를 검사하기 전에 CSV 값을 이 표준 형식으로 정규화한다.

  - 정확한 DEC ID에 대한 영향 맵 행이 있으면 DEC 접두어 행보다 우선한다.
  - 새 DEC나 문서 절을 추가하거나 기존 연결이 달라지면 같은 변경에서 `document-impact-map.csv`를 갱신한다.
  - 전체 문서에는 DEC ID 중복·누락, 존재하지 않는 참조, 상태별 필드 구조, 제목 구조, CSV 목록, 코드 블록 닫힘, 예상 밖의 확정 원문 변경과 작업용·공개용 사본 일치를 자동 검사한다.
  - 자동 구조 검수는 문서 전체에 수행하지만 AI의 의미 검토는 영향 구간에 한정한다.
  - 변경 범위가 여러 시스템에 걸치거나 영향 맵만으로 범위를 확정할 수 없으면 관련 범위를 넓혀 검토하고 그 이유를 보고한다.
  - 전체 활성 DEC와 파생 문서의 의미 검수는 구조·스키마 변경, 콘텐츠 담당자 인계 전, 프로토타입 구현 전, 프로토타입 QA 후와 최종 기획서 작성 전에 수행한다.
  - 부분 동기화 후에도 차단 오류가 발견되면 작업을 재개하지 않고 영향 범위를 다시 계산한다.

## DEC-CONTENT-001 — 공통 콘텐츠 엔트리 구조

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 공통 콘텐츠 엔트리 구조는 작물, 재료, 무기, 주민, 레시피와 보상 묶음처럼 독립적으로 참조되는 콘텐츠에 적용한다.
  - 단순히 두 콘텐츠의 관계만 나타내는 연결 CSV 행에는 공통 엔트리 필드를 반복하지 않는다.
  - 연결 행 자체에 독립적인 판정이나 상태가 필요해지면 별도 콘텐츠 ID를 부여하고 공통 콘텐츠 엔트리 구조를 적용한다.
  - 독립 콘텐츠의 공통 열은 `id`, `kind`, `content_status`, `content_version`, `display_name`, `design_intent`로 구성한다.
  - `id`, `kind`, `content_status`, `content_version`은 AI가 초안을 작성하거나 정규화하고 콘텐츠 담당자가 승인하는 메타데이터다.
  - `display_name`과 `design_intent`는 콘텐츠 기획자가 편집한다.
  - `id`는 승인 후보에서 필수이며 최초 작업용 CSV에서는 비워 두거나 `AUTO`로 표시할 수 있다.
  - AI는 신규 ID를 `kind.고유_이름` 형식으로 제안하며 영문 소문자, 숫자, 밑줄과 마침표만 사용한다.
  - ID는 저장소 전체에서 중복될 수 없고 ID의 첫 구간은 `kind`와 일치해야 한다.
  - 하위 콘텐츠의 ID는 마침표로 구간을 추가할 수 있다.
  - 최초 승인 후에는 표시 이름이나 내용이 바뀌어도 ID를 자동 변경하지 않는다.
  - 승인된 ID를 변경해야 할 때는 일반 편집이 아니라 영향을 받는 모든 참조를 확인하는 별도의 ID 이전 작업으로 처리한다.
  - `kind`는 확정된 데이터 유형만 사용하며 해당 CSV의 데이터 유형, `kind`와 ID 접두어가 모두 일치해야 한다.
  - 새로운 `kind`의 추가는 스키마 변경으로 처리한다.
  - `content_status`는 `draft`, `in_review`, `approved`, `needs_review`, `retired`만 사용한다.
  - 사용하지 않기로 한 미승인 초안은 삭제하고 과거에 승인됐던 콘텐츠만 `retired`로 남긴다.
  - 런타임 JSON은 `approved` 데이터로만 생성하며 작성·승인 관리용인 `content_status`는 런타임 JSON에 포함하지 않는다.
  - 신규 콘텐츠의 최초 승인 후보는 `content_version` 1을 사용한다.
  - 승인된 내용을 의미 있게 수정하면 다음 승인 후보의 `content_version`을 1 증가시키고 콘텐츠 담당자의 승인 시점에 확정한다.
  - 행 정렬, 열 순서와 인코딩 정규화는 콘텐츠 버전 증가 사유로 사용하지 않는다.
  - `content_version`은 디버깅과 재현을 위해 런타임 JSON에 포함한다.
  - `display_name`은 기획자와 AI가 데이터를 식별하기 위한 사람이 읽을 수 있는 이름으로 모든 독립 콘텐츠에 작성한다.
  - `display_name`의 게임 화면 노출 여부는 각 콘텐츠 데이터 구조에서 결정한다.
  - 표시 이름은 중복될 수 있지만 혼동할 정도로 비슷한 이름에는 검증 경고를 표시한다.
  - `design_intent`는 모든 독립 콘텐츠에 필수로 작성하고 해당 콘텐츠의 플레이 역할과 다른 콘텐츠와 구분되는 이유를 한두 문장으로 기록한다.
  - AI는 콘텐츠를 수정하거나 후보를 추가할 때 `design_intent`를 우선 제약으로 사용하며 런타임 JSON에는 포함하지 않는다.
  - 여러 에셋 참조는 공통 엔트리의 한 셀에 넣지 않고 `content_id`, `asset_role`, `asset_id`를 가진 별도의 에셋 연결 CSV에 한 행씩 기록한다.
  - 에셋 참조는 실제 파일 경로가 아닌 논리 에셋 ID를 사용하고 아트가 없으면 연결 행을 만들지 않아도 된다.
  - `asset_role`의 종류와 논리 에셋 ID를 실제 파일에 연결하는 규칙은 `DEC-ART-001`에서 결정한다.
  - 다른 콘텐츠 참조는 범용 `references` 열에 모으지 않고 `reward_bundle_id`, `combat_profile_id`처럼 의미가 드러나는 열이나 별도의 연결 CSV를 사용한다.
  - `schema_version`은 공통 엔트리에 반복하지 않고 전체 데이터 묶음에 한 번만 기록한다.
  - 범용 `tags`는 실제 용도가 생기기 전에는 공통 필드로 추가하지 않는다.
  - 작성자·수정일·승인자와 변경 이유는 Git 이력으로 추적한다.
  - 파일 경로, 행 번호, 필드 경로와 오류 이유는 검증 도구가 자동으로 출력하며 콘텐츠 엔트리에 검증 위치 메타데이터를 저장하지 않는다.

  - 각 일차 시작 시 해당 일차의 일정 행을 읽지만 플레이어에게는 현재 일차와 그날 밤의 습격 여부만 공개한다.

  - 습격 주민과 선택된 사연 시나리오는 습격 예정일의 정비단계에서 `밭을 정찰하러 간다`를 실행해 조우를 시작할 때 불러온다.
  - 일정에는 `final_raid`가 정확히 하나 있어야 하고 반드시 `total_days`에 배치한다.
  - `final_raid`에는 적대 주민이 반드시 있어야 하며 마지막 습격 뒤에 도달할 수 없는 일차를 작성하지 않는다.
  - 마지막 습격이 전투 없이 해결되어도 조우 결과 후 엔딩으로 이동한다.

  - 현재 일차, 현재 단계, 당일 습격 예고 확인 여부, 조우 진행과 결과는 런타임 상태이므로 일정 CSV에 저장하지 않는다.

## DEC-CONTENT-003 — 작물 데이터 구조

  - `is_raw_edible`이 `false`이면 세 생식 수치 필드를 비워 둔다.
  - 생식의 공격 금지, 피격 취소와 완료 시 수확물 1개 소비는 공통 시스템 규칙을 사용하고 작물 데이터에 반복하지 않는다.

  - 전투 보정이 변경할 수 있는 능력치와 실제 배율은 `DEC-CONTENT-009`에서 정의한다.
  - 플레이어 투척 무기의 지속 피해와 이동 둔화는 적대 주민에게 적용한다.
  - 이동 둔화는 주민의 이동속도만 바꾸고 공격 재사용 대기시간과 투사체 속도를 변경하지 않는다.
  - `surrender_health_ratio`는 0 초과 1 미만의 수로 관리한다.

  - 플레이어의 직접 피해, 지속 피해와 지원 공격은 피해를 먼저 적용한 뒤 주민 체력이 0이면 즉시 처치하고 체력이 1 이상이며 투항 기준 이하이면 투항 대화를 시작한다.
  - 실제 주민별 투항 비율은 `DEC-RESIDENT-040`의 콘텐츠·밸런스 작업으로 작성한다.
  - `retreat_reward_bundle_id`는 대가 요구·퇴각 보상 묶음, `kill_reward_bundle_id`는 주민 처치 보상 묶음을 참조한다.
  - 승인된 주민 전투 프로필은 승인된 퇴각 보상 묶음과 처치 보상 묶음을 모두 참조해야 한다.

## DEC-CONTENT-009 — 성격 기반 대화 판정과 전투 보정 데이터 구조

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 선택지 대사, 판정 규칙, 주민 성격 프로필, 성격별 선택 결과, 시스템 결과, 결과별 반응 대사와 전투 보정을 서로 다른 데이터로 관리하고 ID 참조로 연결한다.

  - 실제 전투 효과 수치는 투척 무기 데이터가 소유하고 실제 회복량과 추가 회복 효과는 작물 또는 회복 아이템 데이터가 소유한다.
  - 작물 속성 데이터에는 별도의 회복 효과 열을 만들지 않는다.
  - 작물 속성 자체에는 강화 단계, 레벨과 효과 배율을 저장하지 않는다.
  - 강화는 작물 제작 사용에 따른 숙련도 증가, 숙련도 기준 도달, 상위 레시피 해금과 더 강한 결과물 제작의 흐름으로 처리한다.
  - 작물 속성 데이터에는 레시피 ID와 무기 ID의 역방향 목록을 저장하지 않는다.
  - 작물은 작물 속성을 참조하고 레시피는 필요한 작물과 결과물을 참조하며 투척 무기는 작물 속성과 실제 전투 효과를 참조한다.
  - 필요한 역방향 관계는 승인 데이터에서 런타임 데이터를 생성할 때 자동 계산한다.
  - 시스템이 대표 작물 계통을 결정하면 대표 작물 ID·표시 이름, 작물 속성 ID·표시 이름, `ending_prompt_summary`, 해당 작물의 숙련도와 사용 기록을 엔딩 기록 입력으로 전달한다.
  - `ending_prompt_summary`는 LLM이 엔딩 종류를 결정하는 규칙이 아니라 시스템이 이미 확정한 엔딩을 문장으로 표현할 때 사용하는 승인된 서술 재료다.
  - 작물 속성의 색상, 아이콘과 이펙트 파일은 작물 속성 CSV에 직접 저장하지 않고 공통 에셋 연결 CSV에서 논리 에셋 ID로 관리한다.
  - 작물 속성 데이터 검증은 공통 엔트리 규칙, 필수 설명, 구현된 전투 효과 키, 작물과 속성의 양방향 1:1 관계, 고아 속성, 승인 상태와 중복 저장 금지 규칙을 검사한다.

## DEC-CONTENT-013 — 전투 효과 메커니즘 키와 매개변수 구조

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 1차 프로토타입에서 작물 속성이 사용할 전투 효과 메커니즘 키는 `damage_over_time`과 `movement_slow`로 제한한다.
  - 작물 속성의 표시 이름과 구현 키를 분리하고 서로 다른 작물 속성이 같은 구현 키를 재사용할 수 있다.
  - 효과가 없는 `none` 키는 허용하지 않는다.
  - 새로운 효과 키를 추가할 때는 콘텐츠 값만 추가하지 않고 구현과 스키마 변경을 함께 처리한다.
  - 실제 효과 수치는 작물 속성이 아니라 투척 무기 데이터가 소유한다.
  - 투척 무기의 공통 효과 필드는 `effect_rank`, `effect_duration_seconds`, `effect_damage_per_tick`, `effect_tick_interval_seconds`, `effect_move_speed_multiplier`로 구성한다.
  - 투척 무기는 `crop_attribute_id`를 통해 전투 효과 메커니즘 키를 확인하고 무기 데이터에 같은 키를 중복 저장하지 않는다.
  - `effect_rank`는 1 이상의 정수로 관리하고 효과 수치의 자동 배율이 아니라 같은 효과를 다시 적용할 때의 우선순위로만 사용한다.
  - `damage_over_time` 무기는 `effect_rank`, `effect_duration_seconds`, `effect_damage_per_tick`, `effect_tick_interval_seconds`를 필수로 작성하고 `effect_move_speed_multiplier`는 비워 둔다.
  - 지속 피해의 지속시간과 틱 간격은 0보다 큰 초 단위 수, 틱당 피해는 1 이상의 정수로 관리한다.
  - 지속 피해의 틱 간격은 지속시간보다 클 수 없다.
  - 투척 무기 명중 시 기본 직접 피해를 먼저 적용하고 첫 지속 피해는 즉시가 아니라 첫 틱 간격이 지난 뒤 적용한다.
  - 지속시간 안에 도달한 틱만 피해를 주고 지속 피해도 일반 피해 처리 경로를 사용한다.
  - 지속 피해로 적을 처치하거나 주민의 투항 기준에 도달시킬 수 있고 지속 피해에는 별도의 치명타를 적용하지 않는다.
  - `movement_slow` 무기는 `effect_rank`, `effect_duration_seconds`, `effect_move_speed_multiplier`를 필수로 작성하고 두 지속 피해 수치 필드는 비워 둔다.
  - 둔화 지속시간은 0보다 큰 초 단위 수, 이동속도 배율은 0 초과 1 미만의 수로 관리한다.
  - 둔화는 대상의 이동속도에만 적용하고 공격 주기, 투사체 속도와 애니메이션 속도를 변경하지 않으며 대상을 완전히 정지시키지 않는다.
  - 플레이어 투척 무기의 전투 효과는 재배 단계의 적대 야생동물과 습격 단계의 적대 주민에게 적용한다.
  - 영입 주민의 지원 공격이 전투 효과를 적용할지는 `DEC-CONTENT-008`에서 결정한다.
  - 플레이어에게 적의 상태 효과를 적용하는 기능은 1차 프로토타입 범위에 넣지 않는다.
  - 한 대상은 `damage_over_time`과 `movement_slow`를 각각 하나씩 동시에 가질 수 있다.
  - 같은 효과 키의 여러 효과를 합산하거나 배율로 중첩하지 않는다.
  - 더 높은 `effect_rank`의 같은 효과가 들어오면 기존 효과 전체를 새 무기의 수치와 전체 지속시간으로 교체한다.
  - 같은 `effect_rank`의 같은 효과가 들어오면 가장 최근에 명중한 무기의 효과로 교체하고 지속시간을 새 효과의 전체 지속시간으로 다시 시작한다.
  - 더 낮은 `effect_rank`의 같은 효과가 들어오면 기존 효과를 유지하고 새 상태 효과는 적용하지 않지만 새 무기의 기본 직접 피해는 정상 적용한다.
  - 투척 무기 명중 처리는 기본 직접 피해, 체력 0 확인, 주민 투항 기준 확인, 전투가 계속될 때 상태 효과 적용 또는 갱신 순서로 진행한다.
  - 지속 피해 틱 처리는 틱 피해, 체력 0 확인, 주민 투항 기준 확인, 전투가 계속될 때 다음 틱 대기 순서로 진행한다.
  - 주민 체력이 0이면 즉시 처치하고 체력이 1 이상이며 투항 기준 이하이면 투항 대화를 시작한다.
  - 전투 효과 타이머는 재배·습격의 실제 플레이 시간이 흐를 때만 진행하고 일시정지·대화·정비와 튜토리얼 정지 중에는 멈춘다.
  - 투항 대화 중에는 주민에게 적용된 효과를 제거하지 않고 정지하며 투항 거부 후 전투를 재개하면 남은 시간부터 다시 진행한다.
  - 영입·퇴각·처치로 조우가 끝나거나 야생동물이 죽거나 사라지거나 단계 종료로 대상이 제거되면 해당 대상의 모든 효과를 제거한다.
  - 전투 효과의 이미지와 사운드 파일 경로는 효과 수치 필드에 넣지 않고 공통 에셋 연결 CSV에서 논리 에셋 ID로 관리한다.
  - 범위 피해와 넉백은 상태 효과 메커니즘에 포함하지 않고 투척 무기의 명중·범위 규칙으로 분리한다.
  - 전투 효과 데이터 검증은 지원 키, 효과 순위, 효과별 조건부 필드, 수치 범위, 무기·작물 속성 참조, 효과 필드와 메커니즘 키의 일치와 런타임 변환을 검사한다.

## DEC-CONTENT-015 — 레시피 작성 원본과 연결 CSV 구조

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - `DEC-CRAFT-002`의 제작 논리를 AI와 기획자가 사용할 실제 CSV로 표현하기 위해 레시피 본체와 입력·해금 연결 구조를 별도로 정의한다.
  - 레시피 작성 원본은 공통 콘텐츠 열에 `result_kind`, `result_id`, `result_quantity`, `unlock_type`을 추가한 `recipes.csv`로 관리한다.
  - 레시피의 `kind`는 `recipe`를 사용하고 ID는 `recipe.*` 형식으로 작성한다.
  - `result_kind`는 `throwable_weapon` 또는 `recovery_item`만 사용한다.
  - `result_id`는 제작 결과물의 승인 콘텐츠 ID이며 실제 결과물의 `kind`와 `result_kind`가 일치해야 한다.
  - 한 레시피는 결과물 종류 하나와 결과물 ID 하나만 가지며 부산물과 여러 종류의 동시 결과를 지원하지 않는다.
  - `result_quantity`는 제작 1회당 획득하는 1 이상의 고정 정수 수량이고 무작위 결과 수량을 사용하지 않는다.
  - 승인 투척 무기와 승인 회복 아이템은 각각 정확히 하나의 승인 레시피가 생성한다.
  - 같은 `result_id`를 여러 승인 레시피가 결과물로 참조할 수 없다.
  - 상위 레시피는 기본 레시피와 다른 결과물 ID를 사용한다.
  - 결과물이 하나이므로 별도의 레시피 결과 연결 CSV를 만들지 않는다.
  - 레시피의 작물과 조합 재료 입력은 `recipe_id`, `input_kind`, `input_id`, `quantity`를 가진 하나의 `recipe_inputs.csv`로 관리한다.
  - `recipe_inputs.csv`의 한 행은 레시피와 입력물 하나의 관계를 나타낸다.
  - `input_kind`는 `crop` 또는 `material`만 사용하고 `input_id`의 실제 종류와 일치해야 한다.
  - `quantity`는 제작 1회에 필요한 1 이상의 정수 수량이다.
  - 하나의 승인 레시피는 승인 작물 입력을 1종 이상, 승인 조합 재료 입력을 1종 이상 가져야 한다.
  - 돈은 레시피 입력으로 사용할 수 없다.
  - 동일한 `recipe_id`와 `input_id` 조합을 여러 행에 중복 작성하지 않는다.
  - 기획자가 같은 입력을 중복 작성하면 AI가 수량을 합친 승인 후보를 제안하고 변경 보고서에 해당 정규화를 기록한다.
  - 제작 횟수를 여러 번 지정하면 각 입력의 `quantity`와 결과의 `result_quantity`에 제작 횟수를 곱해 전체 수량을 계산한다.
  - `unlock_type`은 `base` 또는 `crop_mastery`만 사용한다.
  - `unlock_type`이 `base`인 레시피는 런 시작부터 공개하고 제작할 수 있으며 `crop_mastery_unlocks.csv`에 해당 레시피의 해금 행이 없어야 한다.
  - 모든 승인 작물은 자신을 입력으로 사용하는 `base` 레시피가 최소 하나 있어야 한다.
  - `unlock_type`이 `crop_mastery`인 레시피는 `crop_mastery_unlocks.csv`에 정확히 한 해금 행이 있어야 한다.
  - `crop_mastery_unlocks.csv`는 `crop_id`, `required_mastery`, `recipe_id`를 가지며 `required_mastery`는 1 이상의 정수다.
  - 숙련도 해금의 `crop_id`는 해당 레시피의 작물 입력에 포함되어야 한다.
  - 하나의 레시피에 여러 작물 숙련도를 동시에 요구하지 않는다.
  - 숙련도 조건을 충족하기 전에도 상위 레시피의 존재와 해금 조건을 표시하고 해금되면 현재 런이 끝날 때까지 유지한다.
  - 투척 무기 레시피는 결과 무기의 `crop_attribute_id`에 대응하는 작물을 입력으로 반드시 포함해야 한다.
  - 투척 무기 레시피에 다른 작물 입력을 추가할 수 있고 추가 작물은 제작 성공 시 자신의 작물 숙련도를 증가시키지만 결과 무기의 대표 속성을 변경하지 않는다.
  - 회복 아이템 레시피는 대표 작물 속성을 강제로 지정하지 않고 사용된 모든 작물이 제작 성공 시 실제 소비 수량만큼 각자의 숙련도를 얻는다.
  - 상위 회복 아이템의 해금 계통은 `crop_mastery_unlocks.csv`의 `crop_id`로 결정한다.
  - 1차 프로토타입에서는 제작 소요 시간, 제작 대기열, 제작 성공 확률, 제작 실패 결과, 돈을 이용한 직접 제작 비용, 무작위 결과물, 무작위 품질과 결과물 등급을 사용하지 않는다.
  - 사용하지 않는 기능에 해당하는 `craft_duration_seconds`, `queue_order`, `success_rate`, `failure_result_id`, `currency_cost`, `random_result_group_id`, `quality_min`, `quality_max` 필드를 만들지 않는다.
  - 현재 보유 작물 수량, 현재 보유 조합 재료 수량, 현재 제작 가능한 최대 횟수, 지정한 제작 횟수에 필요한 전체 입력 수량과 제작 후 예상 결과 수량은 현재 런 상태에서 계산하고 레시피 작성 원본에 저장하지 않는다.
  - 제작 실행과 원자적 자원 변경은 `DEC-CRAFT-001`, `DEC-CRAFT-003`, `DEC-CRAFT-004`를 따르고 같은 처리 절차를 레시피 콘텐츠 결정에 중복 저장하지 않는다.
  - 레시피 데이터는 필요한 입력, 제작 결과와 해금 방식만 표현한다.
  - 레시피 제작 결과의 이름, 설명, 효과와 아이콘은 `result_id`가 가리키는 결과물 데이터에서 가져오고 레시피에 복사하지 않는다.

## DEC-UI-005 — 판매·구매 정보와 거래 실행 UI

- 상태: 확정
- 결정일: 2026-07-31
- 결정:
  - 거래 대상의 현재 보유 수량과 단가를 표시한다.
  - 지정한 거래 수량에 따른 총액을 거래 실행 전에 표시한다.
  - 구매 실행 전에 거래 후 남는 소지금을 표시한다.
  - 판매 실행 전에 거래 후 남는 수확물 수량을 표시한다.
  - 보유 수량을 초과한 판매와 소지금을 초과한 구매는 실행할 수 없게 한다.
  - 아이템 선택과 거래 실행을 분리하고 `구매` 또는 `판매` 버튼을 눌렀을 때만 거래를 실행한다.
  - 거래가 성공하면 소지금, 보관함, 제작 가능 상태를 즉시 갱신해 표시한다.
  - 거래 처리 중에는 동일한 거래 버튼을 일시적으로 비활성화해 중복 입력을 막는다.
