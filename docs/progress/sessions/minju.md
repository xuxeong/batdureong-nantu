# 작업 로그 — 김민주 (기획 · 콘텐츠 · 레벨)

**Git 커밋에 남지 않는 것만 적는다.** 무엇을 바꿨는지는 `PROGRESS.md`와 diff에 이미 있다.

작성 형식 (해당 없으면 생략):

```
## YYYY-MM-DD 제목

**한 일** — 한두 줄

**왜 이렇게 했나** — 어떤 대안을 검토했고 왜 접었나

**AI가 잘못한 것** — 무엇을 어떻게 잡았나

**막힌 것** — 결정로그에 답이 없는 것. 기획 책임자에게 올릴 목록
```

`AI가 잘못한 것`과 `막힌 것`이 제일 중요하다. 8/8 제출 자료의
「AI 활용 기술 문서」와 「팀원 롤 기술서」를 쓸 때 이 기록이 그대로 재료가 된다.
일주일 뒤에 기억으로 복원하려 하면 대부분 잃어버린다.

직접 타이핑하지 않아도 된다. 작업이 끝날 때 AI에게 "오늘 작업 세션 로그에 정리해줘"라고
요청하면 이 형식으로 정리해준다. 내용만 확인하고 커밋한다.

이 파일은 개인 전용이라 다른 사람과 충돌하지 않는다.

## 2026-08-01 재배 제한시간 수정 중단과 CSV 인코딩 손상 확인

**한 일**

하루 재배 제한시간을 180초에서 60초로 바꾸려 했으나 그 값을 담는 CSV가 저장소에
없어서 중단했다. 확인하는 김에 `data/drafts/resident_combat_profiles.csv` 한 파일만
한글이 깨져 있는 것을 찾았다. 아직 아무것도 고치지 않았다.

**왜 이렇게 했나**

- **값을 다른 곳에 임시로 넣지 않았다.** `farming_duration_seconds`는
  `run_schedules.csv`(11단계) 소유이고 `DEC-PIPELINE-016`이 게임 데이터 하드코딩을
  금지한다. 파일이 없는데 값만 어딘가 적어두면 원본이 두 곳이 된다.
- **깨진 문장을 바로 새로 쓰지 않고 복원 가능 범위를 먼저 쟀다.** `AGENTS.md` 4절이
  "담당자가 수정한 CSV의 의도를 우선 보존"하라고 한다. 내가 지어낸 문장으로 덮으면
  원문 의도가 그대로 사라진다. 손상 방식(CP949 왕복)을 역산해서 살아남은 바이트로
  **증명되는** 글자와 완전히 소실된 글자를 갈랐다. 4행 모두 약 90%는 확정이고
  행당 22~31자만 복원 불가다. 그 자리에 무엇이 올 수 있는지 후보 목록까지 뽑아서,
  두식 행의 `?입 튜토리얼`은 후보에 `영`만 말이 되고 `residents.csv`의
  "대화·영입 시스템의 입문 상대"와 맞아 **영입**으로 확정했다.

**AI가 잘못한 것**

- **git 이력에 원본이 있다고 가정했다.** `9af21bf`(Update resident_combat_profiles.csv)가
  깨뜨린 줄 알고 그 앞 버전을 꺼냈는데 똑같이 깨져 있었다. 손상은 최초 반입 커밋
  `e4f7d49`에 이미 들어 있어서 되돌릴 원본이 없다. 이력이 있으니 복구된다는 가정이 틀렸다.
- **조사하다가 내 작업 스크립트를 똑같은 방식으로 깨뜨렸다.** PowerShell 5.1에서
  `Get-Content -Raw | Set-Content -Encoding utf8`을 썼더니 비ASCII가 전부 망가졌다.
  원인 파일이 어떻게 깨졌는지를 우연히 재현한 셈이다. 원인 추정의 근거가 됐다.
- **`schema/tables/ending_conditions.json`도 깨졌다고 보고할 뻔했다.** PowerShell이
  UTF-8 파일을 ANSI로 읽어서 생긴 표시 문제였고 파일 자체는 정상이었다.
  바이트로 다시 확인해서 걸렀다. **화면에 깨져 보이는 것과 파일이 깨진 것은 다르다.**

**막힌 것**

1. **11단계 CSV 2종이 저장소에 없다.** `run_schedules.csv`(여기에
   `farming_duration_seconds`가 있다), `run_schedule_days.csv`. 10단계 4종과 12단계
   3종도 없다. `e4f7d49` 커밋 메시지는 "콘텐츠 1~9·11~12단계 승인분 일괄 반입"이라고
   적혀 있지만 실제로 들어온 것은 1~9단계뿐이다. 180초를 어디서 봤는지 확인이 필요하다.
2. **손상된 4행의 소실 글자.** 원문을 쓴 사람만 채울 수 있는 자리가 남아 있다.
   특히 이장 행의 `최고 난도 ?업`은 후보에 `졸`이 없어서 무슨 단어였는지 모르겠다.

## 2026-08-02 재반입분 검수

**한 일**

11~12단계 CSV와 성한 `resident_combat_profiles.csv`를 다시 올린 뒤(27374a8, 87efafd)
27종 전부 인코딩을 검사하고 `node tools/validate.mjs drafts`를 돌렸다.
인코딩은 전부 깨끗하다. 승인 상태와 무관한 실제 오류 11건이 남아 있다.

**AI가 잘못한 것**

- **커밋 메시지에 "수치·ID·참조는 동일하므로 content_version은 올리지 않는다"고
  쓰라고 추천했는데 사실이 아니었다.** 재반입분에서 두식 투항선 0.3→0.4,
  만복 0.2→0.3이 같이 바뀌었다. 나는 깨진 파일을 **텍스트 문제로만** 보고
  숫자는 당연히 같을 거라 가정한 채 문구를 만들었다. 파일을 받은 뒤 열별로
  비교하고 나서야 알았다. **추천 문구에 사실 주장을 넣을 거면 그 사실을 먼저
  확인해야 한다.** 다행히 두식은 design_intent의 "투항선 40%"와 데이터가
  0.3으로 어긋나 있던 것이 0.4로 맞아진 것이라 방향은 옳다.
- **`npm run data:validate`가 `data/approved`만 본다는 걸 처음에 놓쳤다.**
  0종이라고 나와서 검사할 방법이 없다고 판단할 뻔했는데,
  `tools/validate.mjs` 헤더에 `drafts` 인자가 문서화돼 있었다. 도구를 쓰기 전에
  도구를 읽었어야 했다.

**막힌 것** (기획 책임자 확정 필요)

1. **`wildlife.csv`의 `player_description` 열이 스키마에 없다.** 플레이어에게
   보여줄 소개 문구라 콘텐츠 값이 아니라 새 필드다. `DEC-PIPELINE-016`이
   임의 열 추가를 금지하므로 내가 지우거나 스키마에 넣지 않았다.
   열을 살리려면 스키마 변경이 필요하고, 야생동물 소개 문구를 어디에 두는지
   결정이 없다.
2. **`data/drafts/`의 `content_status`가 섞여 있다.** 9종은 `approved`,
   9종은 `draft`다. 초안 폴더에 승인 표시가 붙어 있어서 참조 검사가
   반쪽으로 통과한다. 어느 쪽으로 맞출지 정해야 한다.

## 2026-08-02 초안 정리 — 상태 통일·미사용 열 제거·투항선 원복

**한 일**

`content_status` 69행 전부 `draft`로 통일, `wildlife.csv`의 `player_description`
열 제거, 두식·만복 `surrender_health_ratio`를 0.3·0.2로 원복했다.

**왜 이렇게 했나**

- **승인은 나중에 한 번에 하기로 했다.** 초안 폴더에 `approved`가 섞여 있으면
  참조 검사가 반쪽만 통과해서, 무엇이 실제로 검증된 건지 알 수 없다.
  전부 `draft`로 내리면 검증이 "아직 아무것도 승인 안 됨"이라는 사실을
  정직하게 보고한다.
- **차단 오류가 74건에서 164건으로 늘었는데 이게 정상이다.** 전부 `draft`가
  되면서 `require_status: approved` 참조가 모두 걸린 것뿐이다. 승인 상태와
  무관한 실제 오류는 11건에서 10건으로 줄었다(`player_description` 해결).
  **숫자만 보고 나빠졌다고 판단하면 안 된다.**
- **`player_description`을 지웠다.** 야생동물 소개 문구를 보여줄 화면이 없어서
  스키마 변경을 요청할 이유가 없어졌다. 문구 3줄은 git 이력(`87efafd` 이전)에
  남아 있으니 나중에 표시할 곳이 생기면 꺼내 쓸 수 있다.
- **CSV를 직접 문자열 치환하지 않고 `tools/lib/csv.mjs`를 그대로 썼다.**
  따옴표·줄바꿈 처리와 `.gitattributes`의 LF 규칙을 도구와 어긋나지 않게
  맞추려고 했다. diff를 확인하니 의도한 셀 외에는 바뀐 것이 없다.

**AI가 잘못한 것**

- **`npm run test`가 실패하길래 내 변경 탓인 줄 알았다.** 실제로는 이 셸의
  PATH에 `git`이 없어서 `check-docs`가 HEAD의 결정로그를 못 읽은 것이었다.
  PATH를 잡아주니 10개 전부 통과한다. 데이터만 고쳤는데 문서 검사가 깨질
  이유가 없다는 걸 먼저 생각했어야 했다.

## 2026-08-02 ID 접두어 정규화와 문구·수치 정합

**한 일**

`ending_conditions.condition_id`에서 `cond.` 제거, ID 접두어를
`DEC-CONTENT-009`·`DEC-RESIDENT-049`에 맞춰 28개 셀 교체(참조 포함),
두식 `design_intent`의 "투항선 40%"를 데이터(0.3)에 맞춰 "30%"로 고쳤다.
**승인 상태와 무관한 차단 오류가 0건이 됐다.**

**왜 이렇게 했나**

- **문자열 전체 치환을 쓰지 않고 `id`와 `_id`로 끝나는 열만 골라 바꿨다.**
  `design_intent` 같은 본문에 우연히 같은 글자가 있어도 건드리지 않는다.
- **접두어 비교에 `startsWith`를 썼다.** `support_attack_profile.`은
  `resident_support_attack_profile.`의 부분 문자열이라 단순 치환이면 이미 고친
  값에 또 붙어 `resident_resident_...`가 된다. `startsWith`는 앞에 고정되므로
  이미 고친 값은 다시 걸리지 않는다.
- **두식은 문구를 데이터에 맞췄다.** 0.3이 의도한 값이라고 확인받았으니
  틀린 쪽은 문구다. 금례(15%)·이장(10%)은 원래 맞아서 손대지 않았다.

**AI가 잘못한 것**

**퍼센트 대조에서 금례·이장까지 불일치라고 보고할 뻔했다.** PowerShell이
원소 하나짜리 컬렉션을 문자열로 풀어버려서 `$pct[0]`이 배열의 첫 원소가 아니라
**문자열의 첫 글자**를 집었다. "40"이 "4"로, "15"가 "1"로 나와 전부 불일치로
보였다. `@()`로 감싸 고쳤고 실제 불일치는 두식 하나뿐이었다.
**한 건이 아니라 세 건이 틀렸다는 결과가 나왔을 때 데이터를 의심하기 전에
집계 코드를 먼저 의심해야 했다.**

**남은 것**

10단계 4종(`story_infos`, `story_scenarios`, `dialogue_choices`,
`dialogue_choice_responses`)과 12단계 `journal_fallbacks.csv`가 아직 없다.
차단 154건은 전부 "아직 승인 안 됨"이라 일괄 승인 시 사라진다.
