# 작업 로그 — 전성민 (기획)

**Git 커밋에 남지 않는 것만 적는다.** 무엇을 바꿨는지는 `PROGRESS.md`와 diff에 이미 있다.

작성 형식 (해당 없으면 생략):

```
## YYYY-MM-DD 제목

**한 일** — 한두 줄

**왜 이렇게 했나** — 어떤 대안을 검토했고 왜 접었나

**AI가 잘못한 것** — 무엇을 어떻게 잡았나

**막힌 것** — 결정로그에 답이 없는 것. 기획 책임자에게 올릴 목록
```

`AI가 잘못한 것`과 `막힌 것`이 제일 중요하다. 8/8 제출 자료의
「AI 활용 기술 문서」와 「팀원 롤 기술서」를 쓸 때 이 기록이 그대로 재료가 된다.
일주일 뒤에 기억으로 복원하려 하면 대부분 잃어버린다.

직접 타이핑하지 않아도 된다. 작업이 끝날 때 AI에게 "오늘 작업 세션 로그에 정리해줘"라고
요청하면 이 형식으로 정리해준다. 내용만 확인하고 커밋한다.

이 파일은 개인 전용이라 다른 사람과 충돌하지 않는다.

**AI가 잘못한 것**
- 처음에 일지 UI 표시 항목을 `DEC-JOURNAL-005`(보류)로 만들었는데, 이 저장소는 UI 관련 보류 항목을 전부 `DEC-UI-*` 접두어로 통일 관리한다는 걸 놓쳤다. 내가 지적하자 AI가 `DEC-JOURNAL-005`를 로그에서 제거(한 번도 확정된 적 없는 보류라 ID 재사용 금지만 하고 삭제)하고 `DEC-UI-028`로 다시 만들었다.
- `journal_fallbacks.csv`라는 새 테이블을 추가하면서 `schema_manifest.json`의 `schema_version`을 올리는 걸 빠뜨렸다. `schema/README.md`에 명시된 절차인데도 처음엔 놓쳤고, 재확인 과정에서 AI가 스스로 찾아내 1→2로 올리고 `history`에 사유를 남겼다.
- 시스템 기획서·콘텐츠 가이드의 "CSV 31개"를 32개로 고치면서 정작 그 숫자의 근거인 확정 `DEC-PIPELINE-014` 원문은 그대로 둬서, 결정 로그(단일 원본)와 파생 문서가 서로 어긋나는 상태를 만들었다. "모든 문서를 안 읽고 고쳐서 생긴 충돌이 있는지 검수해달라"고 요청하고 나서야 전체 재검토 중에 발견됐다.
- `README.md`, `CLAUDE.md`, `schema/README.md`, 제출용 AI 활용 기술 문서에 "CSV 31종" 표기가 `docs/planning` 밖에도 남아 있었다. `docs:check` 도구가 "31개"라는 정확한 문자열만 하드코딩해서 검사하기 때문에 이런 것도, 다른 위치의 표기도 못 잡는다 — 저장소 전체 grep으로 직접 찾아야 했다.

**막힌 것** — 기획 책임자(나)에게 올릴 목록이 아니라, 김민주·최수정에게 넘겨야 할 확인 사항으로 정리함 (별도 메시지로 전달 예정):

- 커밋 `e4f7d49`는 "1~9·11~12단계"라고 되어 있지만 실제로는 1~9단계 파일만 있음 — 11~12단계 진행 상황 확인 필요.

## 2026-08-03 DEC-UI-022 확정 (일시정지·포커스 이탈)

**한 일** — `DEC-UI-022`를 보류에서 확정으로 전환. 결정 로그, `밭두렁난투_UIUX_준비도_점검.md`(5-2절 순서표·6절 상태표), 시스템·UI/UX 기획서 13절을 동기화. `npm run docs:check`·`npm test` 통과(확정 125 · 보류 49 · 폐기 18, 테스트 23/23).

**왜 이렇게 했나**

- **`DEC-UI-022`를 1번으로 잡은 이유는 순서표 때문만이 아니라 코드가 이미 이 결정을 앞질러 갔기 때문이다.** 로드맵 3-2절 ③번(게임 루프·화면 매니저 골격)이 완료 표시됐는데 그 항목의 근거가 `DEC-UI-022`(보류)였다. `manager.ts:186`에 최수정이 *"자동 재개는 하지 않는다 — 재개 확인 절차는 DEC-UI-022가 보류다"* 라고 주석으로 남겨두고 기다리고 있었다. 보류 DEC를 근거로 코드가 먼저 쓰인 상태를 오래 두면 나중에 어느 쪽이 맞는지 판정해야 한다 — "CSV 31개" 때와 같은 패턴이라 먼저 닫았다.
- **포커스 복귀 시 자동 재개를 접었다.** `DEC-RUN-008`이 체력 0을 전체 런 실패로 확정해 뒀기 때문에, 화면을 보고 있지도 않은 사이에 런이 날아가는 경우가 생긴다. 클릭 한 번 더 하는 비용이 훨씬 싸다. 카운트다운 재개(3·2·1)도 검토했지만 새 연출을 8/4 컷 트리거 앞에서 추가할 자리가 아니라 접었다.
- **`Esc`로 닫히는 오버레이를 회복 퀵메뉴 하나로 좁혔다.** `DEC-INPUT-009`가 "`Esc`: 일시정지 또는 열려 있는 보조 UI 닫기"까지만 정하고 무엇이 "보조 UI"인지는 비워 뒀는데, 그 빈칸을 코드가 "필수 대화만 아니면 닫는다"로 채워 놓은 상태였다. 그래서 정비 허브가 `Esc`로 닫힌다 — `DEC-RUN-006`(하단 진행 버튼으로만 종료)과 어긋난다. 정비 허브에도 확인 창을 띄우는 안(B2)을 검토했지만 종료 경로가 두 개가 되고 습격일·비습격일 버튼 문구를 확인 창에 다시 실어야 해서 접었다.
- **일시정지 화면의 내용물은 `DEC-UI-027`, 중첩 UI 일반 규칙은 `DEC-UI-026`으로 명시적으로 넘겼다.** 문안에 경계를 한 줄씩 박아 두지 않으면 나중에 그 둘을 열 때 같은 결정을 두 번 하게 된다.
- 준비도 점검 문서의 "26개 보류 항목"이라는 표현을 숫자 없이 고쳤다. 확정할 때마다 어긋나는 값이라 이미 3 틀어져 있었다. 시스템 기획서 `갱신일`도 7/31에서 멈춰 있어 함께 고쳤다.

**AI가 잘못한 것**

- **저장소를 다 읽고 현황을 보고했는데 그게 `main` 기준이었다.** 실제 작업은 `develop`에서 14커밋 앞서 있었고, 로컬에 그 브랜치가 없어서 존재조차 확인하지 않았다. 그래서 `enums.json`의 `player_base_stats` 누락, `ci.yml`의 develop 미포함, 8/1 밤 착수 항목 전부를 "아직 안 됨"으로 보고했는데 전부 이미 끝나 있었다. 미작성 CSV도 6종이라 했지만 실제로는 2종이었다. 팀규칙 8절이 "작업을 시작할 때 항상 `git pull` 부터"라고 적어둔 이유가 정확히 이거였는데, 읽기부터 시작했다. **원격 브랜치 목록을 먼저 보는 것이 파일을 읽는 것보다 앞선다.**
- **확인 질문 5번(카운트다운을 보류 DEC로 남길지)은 애초에 물을 일이 아니었다.** `AGENTS.md` 5.2절이 "확정 전 검토에서 채택되지 않은 제안은 기록하지 않는다"로 이미 답을 정해 뒀는데 선택지처럼 냈다. 규칙에 답이 있는 것을 담당자에게 다시 묻는 건 질문 예산을 낭비하는 것이다.

**최수정에게 넘길 것** (로드맵 11-2 표는 소유자가 아니라 여기 적어 둠 — push할 때 전달)

- **표시 이름에 새 테이블을 만들지 않았다.** `resident_combat_modifiers.csv`에 `display_name`이 이미 있고 `DEC-CONTENT-001`이 "`display_name`의 게임 화면 노출 여부는 각 콘텐츠 데이터 구조에서 결정한다"로 열어 뒀다. 여기서 "노출한다"고 정하면 끝난다. 습격 예고(`DEC-RUN-011`)는 담을 열 자체가 없어 새 테이블이 필요했지만 이건 다르다.
- **투항 기준선을 체력 게이지에 표시하지 않기로 했다.** `DEC-RESIDENT-016`이 투항을 무작위 없이 확정적으로 만들어서 표시해도 시스템상 문제는 없다. 그런데 보여주면 플레이어가 "딱 거기까지만" 때리는 계산을 하게 되고 전투가 산수가 된다. 안 보여주면 투항 대화가 열리는 순간이 사건이 된다. 놓칠 위험도 없다 — `DEC-RESIDENT-019`가 투항 대화에서 선택지를 준다.
- **전투 진행도 표시를 만들지 않는다고 명시했다.** `DEC-UI-019`의 재검토 조건에 "전투 진행 상태"가 항목으로 있었지만 습격 전투에는 시간제한이 없다(`DEC-UI-017`이 재배 시간 표시를 습격 모드에서 뺐다). 진행도는 곧 주민의 남은 체력이라 별도 표시를 만들 이유가 없다. 재검토 조건의 항목을 그대로 다 만들지 않고 "만들지 않는다"를 결론으로 적은 것은 `DEC-UI-018`의 "파종 가능 여부"와 같은 처리다.
