## 5. 즉시 처리해야 할 대기 항목

### 5.1 김민주 — P0 셋이 아직 안 들어왔다

확정했는데 반영이 안 됐다. 2026-08-06 확인 결과다.

```

player_base_stats.csv  starting_money 여전히 0. 8이어야 한다
tutorial_steps.csv     sell_crop 3번에 그대로. assign_quickslot 없음
```

**이게 안 들어오면 튜토리얼이 45%에서 막힌다.** 소지금 0인데 `craft_item` 앞에
`sell_crop`이 있어서, 팔고 나면 제작할 작물이 모자란다.

### 5.2 김민주 — 회신 대기 질문 둘

**① 지원 주민 공격이 투사체인가 즉시 적중인가.**
`resident_support_attack_profiles.csv`에 `damage`·`first_attack_delay`·`attack_interval`
셋뿐이고 속도·반경·사거리가 없다. 날아가는 것이면 돌·엽전·부지깽이 그림 3장이 늘고
스키마도 바뀐다. **E단계 투척물이 5장인지 8장인지가 여기서 갈린다.**

**② 주민 넷의 근접 무기가 무엇인가.**
`resident_combat_profiles.csv`에 무기 열이 없다. 낫은 플레이어 전용이다(`sickle_*`).
영순만 사연에 *"처음으로 낫을 들고"* 가 있고, 만복·금례는 지원 공격 이름
(엽전 던지기·부지깽이)에서 유추되며, **이장은 근거가 전혀 없다.** 이장은 맨손 유지를
추천했고 확정 대기 중이다.

### 5.3 최수정 — 아직 안 보낸 메시지

**필드의 조준선을 개발 빌드로 내리는 건.** `src/render/field.ts` 413행이 제출 빌드에서도
조준선을 그리는데, `DEC-INPUT-002`는 *"낫 공격은 마우스 커서 방향을 기준으로 한다"* 로
판정 기준만 정했고 **조준선을 그리라는 규칙이 어디에도 없다.** `DEC-UI-018`이 상호작용
반경 도형을 금지한 정신을 따르면 개발 빌드가 맞다. 메시지 초안은 썼고 전달 전이다.

### 5.4 전성민 본인

**API 키를 촬영 뒤에 반드시 폐기한다.** Vercel 설정이 안 보여서 개인 Anthropic 키를
팀원에게 넘겼다. 저장소가 public이라 키가 커밋되면 즉시 유출된다.
`VITE_` 접두어를 절대 붙이지 않는다 — 브라우저 번들에 들어간다.

## 8. 내가 반복해서 틀린 것 — 같은 실수를 하지 마라

**이 절이 이 문서에서 제일 중요하다.** 저장소를 읽어서는 알 수 없고,
같은 함정에 다시 빠지기 쉽다.

### 8.1 문서에 규칙을 적어놓고 그 규칙을 안 지켰다 — 세 번

```
B2   "부품은 목업의 그것을 가리켜 지목한다" 를 적기 전에, 말로 생김새를 설명해서
     GPT가 새로 디자인했다
C1   그 규칙을 10절에 적어놓고도 또 말로 설명했다. 사용자가 잡았다
SD   6절을 사람(6.1)과 그 밖(6.2)으로 나눠놓고, 필드 SD는 6.2를 따른다고 내가 적어놓고도
     6.1의 일러스트 태그를 넣었다
```

**긴 문서를 쓰면 자기가 쓴 규칙을 잊는다.** 프롬프트를 짤 때마다 해당 절을 다시 열어라.

### 8.2 근거 없이 규칙을 지어냈다

A1 목업에서 HUD 위치를 *"좌상단 체력, 우상단 일차"* 로 썼는데 **그걸 정한 DEC가 없었다.**
사용자가 *"위치를 정한 것도 있고 안 정한 것도 있는 것 같더라고?"* 라고 물어서 드러났다.

**목업이 그대로 UI 명세가 되므로** 임의로 채운 값이 그대로 굳는다.
정해지지 않은 것은 `(위치)`로 비우고 사람에게 물어라.

### 8.3 pull 을 안 하고 남을 틀렸다고 했다

최수정이 `schema_version` 5→6이라고 했는데 내가 4라고 반박했다. **내가 pull을 안 했고
이미 올라와 있었다.** team-rules 8절이 *"작업을 시작할 때 항상 git pull 부터 한다"* 로
이미 말하고 있었다.

### 8.4 이미 검증된 것을 버리고 새로 짰다

`IMG-B-001`이 잘 나온 형식이었는데(영어, *"sole visual authority"*, 부품을 이름으로만
나열) 다음 시트에서 그 형식을 안 쓰고 새로 짰다. **잘 된 것의 형식을 그대로 재사용해라.**

### 8.5 사용자의 제안을 두 번 흘렸다

*"한 명만 뽑아서 스타일 정하고 여러 명을 한꺼번에 뽑는 게 낫지 않나?"* 를 두 번 흘렸다.
세 번째에 *"통일된 스타일을 뽑기 위해 NovelAI를 쓴 건데 통일이 안 돼서 토큰을 소모하고
있어. 파이프라인이 잘못된 거 아냐?"* 라는 말을 들었고, 답은 처음부터 사용자 말이 맞았다.
10절의 시트 규칙을 캐릭터에 적용하면 되는 것이었다.

### 8.6 두 변수를 동시에 움직였다

Vibe Transfer의 Information Extracted와 Reference Strength를 같이 올리고 내리면서
*"참조를 올리면 등신이 안 줄고 내리면 인물이 달라진다"* 고 문서에까지 적었다.
**둘은 서로 다른 일을 한다.** 앞쪽만 내리면 됐다.

프롬프트를 고칠 때도 마찬가지다. **한 번에 하나만 바꿔라.** 여러 개를 같이 바꾸면
무엇이 들었는지 못 가린다.

### 8.7 네거티브를 과하게 넣어 반대로 갔다

*"따뜻한 색감을 빼달라"* 는 요청에 `warm colors, warm lighting, orange tint, golden hour,
sepia`를 전부 네거티브에 넣었더니 **아예 푸른 계열로 칠해서 나왔다.**
`sun-tanned skin`도 너무 세서 명암이 사라지고 평평한 갈색이 됐다.

**한 단계만 밀어라.** 되돌리는 데 더 많은 토큰이 든다.

## 9. 이 사람과 일하는 방식

```
push 는 시켰을 때만 한다        커밋하고 "push 대상 N건" 이라고 보고한 뒤 기다린다
--force · squash · 이력 수정 금지  제출 요건에 "커밋 기록을 유지해 주세요" 가 있다
결론을 먼저 말한다              근거는 그 뒤에
DEC ID 를 근거로 답한다          "아마" 나 "보통은" 으로 답하지 않는다
답이 없으면 "결정되지 않음"      구현 편의나 재미를 이유로 규칙을 만들지 않는다
작업 단락이 끝나면 세션 로그      docs/progress/sessions/seongmin.md 에 묻지 말고 쓴다
```

**틀렸을 때는 짧게 고치고 넘어간다.** 사과를 길게 쓰거나 반성문을 쓰지 않는다.
무엇이 틀렸고 무엇이 맞는지만 적는다.

**확정 DEC 의 제목과 결정 텍스트는 불변이다.** 오탈자 수정도 대상 ID·이유·바뀌는 문장을
먼저 알리고 승인을 받는다. 의미가 바뀌면 덮어쓰지 않고 **폐기 + 새 숫자 ID 대체**다.
