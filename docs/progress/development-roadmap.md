## 1. 작업을 나누는 기준

코드는 대부분 Claude Code가 쓴다. 그래서 분담 축은 **난이도가 아니라 "틀렸을 때 어떻게 알아채는가"** 다.

| | 최수정 | 김민주 |
|---|---|---|
| 맡는 성격 | 화면으로 확인이 안 되는 것 | 실행하면 눈으로 바로 보이는 것 |
| 구체적으로 | 씬 상태 머신, 자원·관계·공포도 상태, 원자적 처리, 대화·전투 판정 규칙, 데이터 계약, LLM 연동, 통합, 배포 | HUD·상점·제작·대화 화면, 기획자 UI 사진 대조 조정, 데이터 바인딩 확인, 플레이 테스트 |
| 사람이 해야 하는 일 | **AI가 쓴 코드를 읽어야 한다.** 하드코딩·임시 기본값·부분 반영은 실행해도 안 보이고 나중에 밸런스 붕괴로만 드러난다 | **실행해서 봐야 한다.** 결과가 화면에 드러나므로 AI 산출물을 병렬로 돌려도 안전하다 |

최수정 영역에서 특히 사람이 눈으로 확인해야 하는 것 (AI가 자주 어기는 지점):

- 작물·가격·확률·시간·좌표·보상 수치가 코드에 박혔는가 → 전부 런타임 JSON에서 읽어야 한다 (`DEC-PIPELINE-016`)
- 데이터가 없을 때 `?? 기본값`으로 넘어가는가 → 검증 오류로 보고해야 한다
- 거래·제작·자원 협상·보상 지급이 중간에 실패하면 절반만 반영되는가 → 원자적이어야 한다
  (`DEC-RESOURCE-011`, `DEC-CRAFT-004`, `DEC-RESIDENT-033`, `DEC-RESIDENT-042`)
- 엔딩·일지 프롬프트 문장이 코드에 복사됐는가 → 프롬프트 원본 파일 한 곳에서 읽어야 한다 (`DEC-PIPELINE-012`, `DEC-JOURNAL-004`)

## 2. 화면 구성 방식 (기획자 UI 사진을 반영하는 방법)

`index.html`이 이미 두 영역으로 나뉘어 있고, 이 구조를 그대로 쓴다.

```
#game  → 필드. Canvas 2D 한 장. 플레이어·작물·야생동물·주민·투사체 (src/render/)
#ui    → 오버레이. DOM. HUD·정비 허브·대화·결과·엔딩         (src/ui/)
```

`DEC-UI-014` 확정본이 이 구조와 그대로 맞는다. **정비는 별도 화면 전환이 아니라
셔터가 필드를 덮고 그 위에 정비 허브 UI가 올라오는 오버레이**이고, 전투 전 대화와 투항 대화도
필드(습격 모드) 위 오버레이다. 즉 이 둘이 열릴 때 **캔버스는 계속 살아 있고 시뮬레이션만 멈춘다**(9-2절).
독립 화면으로 전환되는 것은 타이틀·이름 입력·튜토리얼·일차 시작·조우 결과·밤 결과·런 실패·엔딩뿐이다.

런 실패와 엔딩은 **공유 템플릿으로 묶지 않고 각각 따로 만든다** (`DEC-UI-014`).

필드는 실시간 액션이라 캔버스가 맞고, UI는 DOM이어야 사진을 보고 위치를 빨리 옮길 수 있다.
**기획자 사진대로 조정하려면 다음 두 가지가 필요하다.**

1. **기준 해상도를 오늘 정한다.** (`DEC-UI-025` 보류 항목)
   예: 1280×720 고정 후 창 크기에 맞춰 비율 유지 스케일.
   기준이 없으면 사진의 "여기쯤"을 옮길 좌표계가 없다.
   **기획팀이 UI/UX와 아트 규격을 정해 전달할 예정**이므로 오늘 확정을 기다리지 않고 진행한다.
   월드 단위 → 픽셀 배율도 아트 규격과 함께 온다. 그때까지는 임시 배율 상수 하나로 그리되
   **`src/render/camera.ts` 한 곳에만 둔다.** 규격이 오면 그 값만 바꾸면 된다.
   (화면 배율은 표현이지 게임 데이터가 아니므로 CSV로 뺄 필요는 없다.)
2. **UI 수치를 한 파일에 모은다.** `src/ui/layout.css`의 CSS 커스텀 프로퍼티로
   패널 위치·크기·여백·색을 선언하고, 각 UI 파일은 변수만 참조한다.
   사진을 받으면 **이 파일의 값만 고친다.** TS 코드를 건드리지 않으므로 김민주 담당 영역 안에서 끝나고
   최수정 작업과 충돌하지 않는다.

보조로, 개발 빌드에서 UI 요소 경계선과 좌표를 겹쳐 보여주는 토글을 `src/ui/dev/`에 둔다.
사진과 대조할 때 픽셀 단위로 맞추기 쉽다. (`VITE_BUILD_MODE=dev`에서만 동작)

> UI 레이아웃 수치는 `DEC-PIPELINE-016`이 말하는 "변경 가능한 게임 데이터"가 아니다.
> CSV로 뺄 필요 없고 CSS 변수로 충분하다. 반대로 작물 성장 시간·가격·확률은 CSS에도 TS에도 두지 않는다.

| 항목 | 없으면 막히는 작업 | 기한 |
|---|---|---|
| **1~2단계 CSV 승인** (`maps`, `farm_plots`, `crop_attributes`, `crops`, **`player_base_stats`**) | 8/2 데이터 로더·재배·플레이어 이동 전체 | **8/2 오전, 최우선** |

| CSV 10종 (10~12단계) | 대화·엔딩·일지 전부 | 8/2~8/3 순차 |
| `data/approved/` 승인 담당·시점 | 8/2 이후 모든 데이터 바인딩 | 8/2 오전 |

첫 줄이 특히 중요하다. 1~9단계 초안은 이미 `data/drafts/`에 있으므로 **전부 승인할 필요 없이
맵·작물·플레이어 수치 5종만 먼저 `data/approved/`로 올리면** 8/2 김민주의 로더와 재배 작업이 바로 돌아간다.
지금은 `data/approved/`가 비어 있어 `npm run data:build`가 아무것도 만들지 못한다.

`player_base_stats.csv`는 스키마만 신설됐고(`DEC-CONTENT-019`, `schema_version` 3) **행이 아직 없다.**
`move_speed`가 없으면 플레이어가 못 움직이고 `max_health`가 없으면 런을 시작할 수 없으므로
이 파일은 맵·작물과 같은 순위로 급하다. 승인 행은 정확히 하나여야 한다.

UI/UX(`DEC-UI-*`)와 아트 규격(`DEC-ART-001`)은 **기획팀이 작업 중이며 정해지는 대로 전달**한다.
개발은 기다리지 않고 진행한다. UI 위치·크기는 사진을 받은 뒤 `layout.css` 값만 고치면 되고(2절),
필드는 플레이스홀더로 그리므로 규격 확정 전에도 막히지 않는다.

CSV 10종은 한 번에 다 필요한 게 아니다. **필요한 순서**는 다음과 같다.

1. `run_schedules`, `run_schedule_days` → 8/2 오전 (일차 흐름)
2. `story_scenarios`, `story_infos`, `dialogue_choices`, `dialogue_choice_responses` → 8/3 밤 (조우 판정)
3. `fear_bands`, `endings`, `ending_conditions`, `journal_fallbacks` → 8/4 밤 (엔딩 판정)

이 순서대로만 나오면 개발은 안 막힌다.
현재 `data/approved/`는 비어 있고 초안도 22종뿐이라, **승인 흐름(`drafts → candidates → approved`)이
8/2 오전에 한 번은 끝까지 돌아본 상태**여야 한다.

  - `progress` job은 main 전용으로 제한 (개발 중 봇 커밋이 안 생겨 pull 충돌이 준다)

  - 시스템 ↔ UI 이벤트 계약 — UI는 상태를 직접 쓰지 않고 이벤트로 요청, 시스템이 확정 후 결과 이벤트 발행

- [ ] **③ 게임 루프 + 화면 매니저 골격** (60~90분)
  - 고정 timestep 루프, 일시정지·포커스 이탈 정지 (`DEC-UI-022`, `DEC-INPUT-009`)
  - **화면은 평평한 씬 목록이 아니다** (`DEC-UI-014`). 세 층위로 나눠 선언한다
    - 독립 화면: 타이틀 / 이름 입력 / 튜토리얼 / 일차 시작 / 조우 결과 / 밤 결과 / 런 실패 / 엔딩
    - 베이스 화면: **필드 하나**. `재배 모드`와 `습격 모드` 두 가지로 동작한다
    - 필드 위 오버레이: 정비 허브(셔터 + 보관함·상점·제작) / 전투 전 대화 / 투항 대화 / 일시정지
  - 흐름은 `DEC-RUN-014`, 결과 화면 규칙은 `DEC-RUN-015`. **`취침` 단계는 없다.**
    습격 없는 날은 정비 종료(`아침까지 잔다`) → 밤 결과 → 다음 일차이고,
    `조우 결과`와 `밤 결과`는 같은 층위로 **하루에 하나만** 등장한다
  - 완료 조건: 콘솔에서 화면 전환이 순서대로 찍히고, 습격일/비습격일 두 경로가 갈린다. 내용은 비어 있어도 된다
- [ ] **④ 입력 계층** (30~60분) — `DEC-INPUT-001~009` 확정본 그대로
  - WASD 이동, 마우스 조준, `E`, 우클릭(낫), 좌클릭(투척), `1~5`, 휠, `Q` 짧게/길게, `Esc`
  - 입력 잠금 상태(대화 중 필드 입력·타이머 정지) 포함
  - `DEC-INPUT-010`(회피·대시) `DEC-INPUT-011`(연속 발사)은 **보류이므로 구현하지 않는다**
- [ ] ⑤ 캔버스 최소 루프 (시간이 남으면)
  - 사각형 플레이어가 WASD로 움직이고 마우스 방향으로 조준선이 돈다 + 카메라
  - 이게 있으면 8/2 김민주의 재배 로직을 화면에서 바로 확인할 수 있다
  - `move_speed`·`collision_radius`는 `player_base_stats.csv`에서 온다 (`DEC-CONTENT-019`).
    승인 전이라 임시 값으로 움직여 볼 수는 있으나 **승인되는 즉시 데이터 경유로 교체**하고,

## 7. 충돌 방지와 협업 규칙

### 7-1. 브랜치

```
develop  → 개발은 전부 여기서. Vercel 프리뷰 URL이 붙는다
main     → 1차 빌드 병합 후 "언제 열어도 시연 가능한 상태". Vercel 프로덕션 URL
```

- **브랜치가 충돌을 줄여주지는 않는다.** 두 사람이 develop 하나에 커밋하면 충돌 양상은 main 하나 쓸 때와 같다. 충돌을 막는 건 아래 파일 소유 규칙이다
- 도입 이유는 **main을 안정판으로 고정**하는 것이다. 8/8 촬영 중 누가 develop에 push해도 촬영용 URL이 안 깨진다
- 병합은 `develop → main` 방향만. **`--no-ff`를 쓰고 squash·force push는 금지**한다 (제출 요건: 커밋 기록 유지)
- 병합 시점에 태그를 단다 (`v0.1-build1` 등). 되돌릴 지점이 명확해진다
- 급한 수정도 main에 직접 커밋하지 않는다. develop을 거치지 않으면 다음 병합에서 갈라진다
- 중간 상태가 깨지는 큰 작업만 develop에서 짧은 feature 브랜치를 판다. 하루 안에 되돌린다

**CI 설정을 같이 바꿔야 한다.** 현재 `ci.yml`은 `push: branches: [main]`이라
**develop에 push해도 검증이 돌지 않는다.**

- `push.branches`에 `develop` 추가 → `data:validate` / `docs:check` / `test`가 개발 중에도 돈다
- `progress` job은 main 전용으로 제한 → 개발 중 `PROGRESS.md` 봇 커밋이 생기지 않아 pull 충돌이 준다.
  작업 기록은 main 병합 시점에 한 번에 갱신된다
- `docs/team-rules.md` 3절("main 직접 작업으로 충분")도 같이 고친다

### 7-2. 파일 소유

| | 최수정 | 김민주 |
|---|---|---|
| 전담 | `src/core/`, `src/state/`, `src/scenes/`, `src/input/`, `src/render/`, `src/systems/combat.ts`, `encounter.ts`, `src/llm/`, `api/`, `schema/`, `tools/`, `.github/` | `src/systems/farming.ts`, `economy.ts`, `src/data/loader.ts`, `src/ui/` 전체 |
| 공용 | `index.html`, `package.json`, `src/main.ts`, `src/data/types.ts`, `src/data/run-config.ts`, `src/state/types.ts`, `data/approved/` — 건드리기 전에 말한다 | 좌동 |

타입 파일은 **최수정이 8/1 밤에 확정해서 커밋**한다. 이후 변경이 필요하면 상대에게 먼저 말한다.
말없이 타입을 고치면 상대 작업이 통째로 안 켜진다.

> 이 분담은 팀규칙 4절의 기본 담당(김민주 = `data/`)과 다르다. **이번 스프린트 한정**이며,
> 비는 콘텐츠 CSV 작업은 전성민이 맡는 것을 전제로 한다. 그게 아니면 8/2 이후 데이터 담당이 없다.

### 7-3. 작업 규칙

- 작업 시작 전 항상 `git pull`. 상대가 밤사이 올린 커밋 위에서 시작해야 한다.
  main에서는 CI 봇 커밋(`PROGRESS.md`)도 생기므로 병합 전후로 특히 주의한다
- 커밋 태그는 팀규칙 2절: `[Feat] [Fix] [Data] [Docs] [Art] [Refactor] [Test] [Chore]`
- 22:00 바통 터치 — 김민주가 push하고 한 줄로 "어디까지 됐고 뭐가 안 됨"을 알린다. 최수정은 pull부터
- 리소스를 추가하는 커밋에서 `docs/submission/CREDITS.md`를 같이 갱신한다 (몰아서 하면 프롬프트를 기억 못 한다)
- `.env`, `generated/runtime/*.json`은 커밋하지 않는다
- 규칙이 없거나 모순되면 임의로 CSV 열을 늘리거나 코드에 예외를 만들지 말고 멈추고 보고한다 (`AGENTS.md` 5절)
- 작업 단락이 끝나면 `docs/progress/sessions/<본인>.md`에 **왜 그렇게 했는지**를 남긴다

## 9. 구현 세부 보완 사항

일자별 작업에 다 적기 어려운, 빠뜨리기 쉬운 구현 지점이다. 해당 작업을 할 때 이 항목을 같이 본다.

### 9-1. 카메라와 좌표 변환 (`src/render/camera.ts`) — 8/1 밤 ~ 8/2, 최수정

`maps.csv`에 `world_width` / `world_height`가 있고 뷰포트보다 클 수 있다.
월드 → 스크린 변환과 플레이어 추적 카메라를 렌더 진입점에 둔다.

- 월드 단위 ↔ 화면 픽셀 배율은 아트 규격이 오기 전까지 이 파일의 임시 상수 하나로 둔다 (2절).
  플레이스홀더로 그리는 동안은 값이 무엇이든 동작하고, 규격이 오면 이 한 줄만 바꾼다
- 카메라는 맵 경계 밖을 비추지 않게 클램프한다
- 같은 좌표계를 쓰는 것: `farm_plots`의 `x/y`, `farm_interaction_radius`,
  `wildlife_spawn_edge_margin`, `wildlife_spawn_min_player_distance`, `attack_range`, `projectile_max_range`
- **변환 함수는 한 곳에만 둔다.** 시스템마다 따로 계산하면 상호작용 판정과 렌더 위치가 어긋난다

### 9-2. 대화 중 입력·진행 정지 (`DEC-INPUT-009`, `DEC-RESIDENT-039`) — 8/3~8/4

대화 모달이 열리면 `src/input/`의 입력 잠금을 켜고, **필드 시뮬레이션 자체를 정지**한다.

정지 대상을 정확히 하면 다음과 같다.

- 플레이어 이동·조준·공격·상호작용 입력
- 주민 AI 추적과 공격, 비행 중인 투사체, 상태이상 지속 틱
- 진행 중인 회복 — 회복은 대화 전환 시 **취소**된다(소비 없음). 정지 후 재개가 아니다
- 재배 제한시간 타이머는 재배 단계 전용이라 대화 시점에는 이미 멈춰 있다. 정비 단계에는 시간제한이 없다

투항 대화는 전투 중간에 끼어들므로 **정지 → 선택 → 재개** 경로가 실제로 필요하다 (`DEC-RESIDENT-039`).
정지 시점의 적 위치·체력·상태이상이 그대로 복원돼야 한다.

`DEC-UI-014`가 확정한 것 두 가지를 같이 지킨다.

- 전투 전 대화와 투항 대화는 **필수 화면이라 `Esc`로 닫을 수 없다**
- 어떤 화면에서도 `Esc`는 일시정지를 연다. 필수 대화 중이라면 **대화는 그대로 둔 채 일시정지만** 겹친다

> 중첩 UI의 표시 우선순위(`DEC-UI-026`)는 여전히 보류다. 위 두 줄 외에 잠금 스택을 임의로
> 설계하지 말고 "대화 열림 = 필드 정지" 규칙만 구현한다.

### 9-3. LLM 실패 처리 — 환경 분기를 만들지 않는다 (`DEC-JOURNAL-003`, `DEC-CONTENT-011`) — 8/4

> 8/1 팀 합의: 로컬 전용 모킹 분기 대신 아래 방식으로 간다.

로컬에서 `/api/*`가 없어도 게임이 멈추면 안 된다는 요구는 그대로 만족시키되, **환경 분기로 풀지 않는다.**

- 확정 규칙은 "실패 시 같은 입력으로 **한 번 재시도**하고, 그래도 실패하면 폴백"이다.
  로컬만 재시도를 건너뛰면 프로덕션에서 처음 도는 경로가 생긴다
- `.env.example`이 이미 답을 적어 두었다 — 키가 비어 있으면 "사용할 수 없는 LLM 환경"으로 처리되어
  폴백을 쓰는 것이 **기획서상 정상 경로**다. 로컬 404도 같은 실패로 취급하면 끝이고 별도 분기가 필요 없다
- 즉 `src/llm/client.ts`는 환경을 구분하지 않는다. 호출 실패(네트워크·404·5xx·타임아웃·형식 위반)를
  전부 같은 실패로 보고 → 1회 재시도 → 폴백. 그러면 로컬에서도 자동으로 폴백이 뜨고 재시도 경로도 같이 검증된다
- 폴백 출처: 일지는 `journal_fallbacks`(공포도 구간 × 변화 방향), 엔딩은 `endings.fallback_record_text`.
  둘 다 승인 데이터에서 오며 코드에 문장을 두지 않는다
- 로컬에서 실제 LLM 경로까지 확인하려면 `vercel dev`로 실행한다. 코드에 넣을 문제가 아니라 실행 방법 문제다

### 9-4. 일지 프롬프트와 매니페스트 (`DEC-PIPELINE-012`, `DEC-JOURNAL-004`) — 8/4

`schema/journal_prompt_system.md`를 만들 때 `schema_manifest.json`도 같이 손댄다. 세 곳이다.

- `"journal_prompt_version": 1` 추가
- `version_change_reasons`에 언제 올리는지 한 줄 추가 (엔딩 프롬프트 항목과 같은 형식)
- `history`에 이번 변경 기록 추가

현재 저장소에는 `ending_prompt_system.md`도 없다. 두 파일 모두 8/4에 새로 만든다.

### 9-5. 런 리셋 (`DEC-RESOURCE-004`, `DEC-RESIDENT-047`) — 8/5

새 런 시작과 런 실패 후 타이틀 복귀에서 전역 상태를 원자적으로 되돌린다.

리셋 대상: 소지금 / 보관함 4종(수확물·재료·무기·소모품) / 투척 퀵슬롯 편성 / 회복 파우치 /
작물 숙련도 / 해금된 레시피 / 주민 런 상태와 관계 / 공포도 / 경작지 상태 / 현재 일차·단계 /
주민별 선택된 사연 시나리오 / 생성된 일지 기록

주의할 점:

- **초기값은 데이터에서 읽는다.** 시작 체력·소지금이 아직 미정이다 (5-1절). 정해지기 전에는 코드에 숫자를 넣지 않는다
- 튜토리얼 자원은 본 런으로 넘어오지 않는다 (`DEC-RESOURCE-004`). 튜토리얼은 별도 상태로 돌린다
- 부분 리셋이 남으면 두 번째 런에서만 재현되는 버그가 된다. 상태 객체를 새로 만들어 통째로 교체하는 편이 안전하다
- 엔딩 수집 같은 런 밖 영구 데이터는 이번 범위가 아니다 (`DEC-RESOURCE-004` 마지막 줄)

### 9-6. 자원 변경의 원자성 — 8/3~8/4

"검증 → 차감 → 지급"을 분리하지 않고 사전 검증 후 한 번에 반영한다. 적용 대상과 근거는 다음과 같다.

| 처리 | 근거 |
|---|---|
| 상점 판매·구매 | `DEC-RESOURCE-011` — 조건 미달이면 소지금과 보관함을 **모두** 변경하지 않는다 |
| 거래 확정 | `DEC-RESOURCE-013` — 버튼을 누르는 순간 현재 소지금·보유 수량을 **다시 검증**한다 |
| 제작 | `DEC-CRAFT-004` — 여러 개 제작 시 부분 성공을 만들지 않는다 |
| 자원 협상 | `DEC-RESIDENT-033` — 수확물 차감과 관계 변경을 함께 반영한다. 거절이면 아무것도 소비하지 않는다 |
| 퇴각·처치 보상 | `DEC-RESIDENT-042` — 지급과 주민 상태 변경을 함께, 중복 지급 방지 |

구현 형태는 "현재 상태 사본에 전부 적용해 보고, 전부 성공했을 때만 실제 상태로 교체"가 가장 단순하다.

보관함 하나만 원자적으로 바꾸면 된다.

## 10. 매일 쓰는 프롬프트

`AGENTS.md`와 결정 로그는 AI가 알아서 읽는다. **여기에 규칙을 다시 적지 않는다.**
아래 절차를 문서에 두었으므로 매일 칠 것은 한 줄이면 된다.

### 10-1. 시작

```
2026-08-03, 최수정. 개발 로드맵 10-1대로 시작하자.
```

이 한 줄을 받으면 AI는 다음을 순서대로 한다.

1. `git pull`, 현재 브랜치가 `develop`인지 확인
2. 이 문서 4절에서 **그 날짜의 해당 작업자 항목**을 읽는다
3. `git log`로 마지막 세션 이후 상대가 올린 커밋을 확인한다
4. `data/approved/`와 `generated/runtime/` 상태를 확인한다 — 오늘 작업의 선행 데이터가 있는가
5. `docs/progress/sessions/` 최근 기록에서 **하다 만 것**을 확인한다
6. 오늘 작업에 걸린 DEC의 상태를 확인한다

그리고 **작업을 시작하기 전에** 다음 세 가지를 보고하고 확인을 받는다.

- 오늘 할 일 (4절 기준)
- 지난 세션 이후 달라진 것
- **결정되지 않아 막히는 것** — 있으면 임의로 채우지 않고 먼저 묻는다

마지막 항목이 핵심이다. 이게 없으면 AI가 보류 DEC를 자기 판단으로 채우고 시작한다.

오프라인에서 정해진 것(구두 합의, 기획팀 회신 등)은 AI가 알 수 없으므로 그것만 한 줄 덧붙인다.
예: `player_base_stats.csv 승인 행 올라갔어.`

### 10-2. 마무리

```
오늘 작업 마무리. 로드맵 10-2대로.
```

AI가 하는 일.

1. 변경된 범위에 해당하는 검증 실행 (`data:validate` / `docs:check` / `test`)
2. 실행하지 못한 검증과 남은 위험 보고
3. `docs/progress/sessions/<본인>.md`에 세션 기록 — 커밋에 남는 "무엇을"이 아니라
   **왜 그렇게 했는지, 접은 대안, 결정로그에 답이 없어 막힌 것**
4. 4절 완료 조건 대비 어디까지 됐는지, 못 맞춘 채 넘어간 것이 있는지 명시
5. **11절 점검** — 오늘 작업에서 계획에 없던 필요 작업이 드러났으면 11-2 표에 추가하고,
   완주 경로(11-1)에서 오늘 상태가 바뀐 줄을 갱신한다
6. 커밋 메시지 초안 제안 (팀규칙 2절 태그)

3번이 8/7 「AI 활용 기술 문서」와 「팀원 롤 기술서」의 재료다. 그날 안 쓰면 대부분 잃어버린다.
4번을 빠뜨리면 다음 작업이 안 된 것을 전제로 깔고 쌓인다.
5번을 빠뜨리면 마지막 날에 한꺼번에 드러난다.

### 10-3. 막혔을 때

```
결정로그에 답이 없는 것 같다. AGENTS.md 5.1 형식으로 정리해줘. 임의로 채우지 말고.
```

CSV에 열을 추가하거나 코드에 예외를 만들어 우회하는 것이 가장 흔한 사고다.
막혔다고 느끼면 진행시키지 말고 이 한 줄을 쓴다.

### 11-2. 계획에 없었는데 필요한 것으로 드러난 것

작업하다 나온 것을 그때그때 여기 적는다. 기억해 두었다가 나중에 적으면 대부분 잃어버린다.

| 발견일 | 항목 | 왜 필요한가 | 담당 | 언제 | 티어 |
|---|---|---|---|---|---|
| 8/2 | LLM 모델 ID를 어디에 둘지 | `DEC-PIPELINE-012`가 "생성 모델 변경은 프롬프트 버전 사유가 아니고 `generator_model_id`로 구분"이라고 정해 모델은 교체 가능해야 한다. 코드에 박으면 그 취지가 깨진다. `ANTHROPIC_MODEL` 환경변수 안이 유력 | 최수정 | 8/4 | P1 |
