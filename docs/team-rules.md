# 팀 작업 규칙

세 명이 같은 저장소에서 12일 동안 작업하면서 충돌과 사고를 줄이기 위한 규칙이다.
기획 규칙은 `AGENTS.md`가 담당하고, 이 문서는 **저장소 사용 방법**만 다룬다.

---

## 1. 시작 전 한 번만 설정

### Git 사용자 이름 통일

제출물의 「팀원 롤 기술서」는 각자가 실제로 맡아 구현한 영역을 적어야 하고, 그 근거가 Git 이력이다.
이름이 갈리면 한 사람이 여러 명으로 집계된다. **각자 아래를 한 번 실행한다.**

```bash
git config user.name  "본인 이름"      # 전성민 / 김민주 / 최수정
git config user.email "GitHub 계정 이메일"
```

`git log --format="%an <%ae>"`로 확인한다. 이미 잘못된 이름으로 커밋했다면 그대로 두고
다음 커밋부터 맞춘다. 이력을 고쳐 쓰지 않는다.

### 환경변수

```bash
cp .env.example .env
```

`.env`는 `.gitignore`에 있다. **저장소가 공개(public)이므로 API 키가 커밋되면 즉시 유출된다.**
커밋 전에 `git status`로 `.env`가 올라가지 않는지 확인한다.

## 2. 커밋

### 태그 컨벤션

커밋 메시지는 대괄호 태그로 시작한다. `PROGRESS.md`가 이 태그로 작업을 분류한다.

| 태그 | 용도 |
|---|---|
| `[Feat]` | 새 기능 |
| `[Fix]` | 버그 수정 |
| `[Data]` | 콘텐츠 CSV 추가·수정·승인 |
| `[Docs]` | 기획 문서, README, 결정로그 |
| `[Art]` | 이미지·사운드·폰트 등 리소스 |
| `[Refactor]` | 동작 변화 없는 구조 개선 |
| `[Test]` | 테스트 추가·수정 |
| `[Chore]` | 설정, 빌드, 의존성 |

```
[Feat] 재배 단계 파종·성장 상태 전환 구현
[Data] crops.csv 승인 후보 8행 추가
[Docs] DEC-PIPELINE-003 확정 반영
```

### 무엇을 남기나

- **왜 바꿨는지**를 남긴다. 무엇을 바꿨는지는 diff가 이미 말해준다.
- 의미 있는 변경은 버전을 올리고 이유를 커밋에 남긴다. (`AGENTS.md` 7절)
- 형식 정규화만으로 콘텐츠 버전을 올리지 않는다.

### 금지

- **`--force` 푸시와 이력 squash 금지.** 제출 요건에 *"커밋 기록을 유지해 주세요"* 가 있다.
- 사용자 변경과 무관한 파일을 되돌리거나 덮어쓰지 않는다.
- `.env`, `node_modules/`, `dist/`, `generated/runtime/*.json` 커밋 금지.

## 3. 브랜치

폴더가 담당자별로 나뉘어 있어 대부분 `main` 직접 작업으로 충분하다.
다만 다음 경우에는 브랜치를 판다.

- 여러 파일에 걸치고 중간 상태가 깨지는 작업
- 다른 사람이 쓰는 파일을 건드려야 하는 작업
- 되돌릴 가능성이 있는 실험

```
feat/farming-growth
fix/quickslot-switch
data/crops-step2
```

---

## 4. 담당 영역과 공용 파일

| 담당 | 주 작업 폴더 |
|---|---|
| 전성민 | `docs/planning/`, `docs/governance/` |
| 김민주 | `data/drafts/`, `data/candidates/` |
| 최수정 | `src/`, `tools/`, `schema/`, `api/` |

**공용 파일** — `data/approved/`, `docs/submission/`, `README.md`, `package.json`

공용 파일을 고칠 때는 커밋을 작게 유지하고 바로 푸시한다. 오래 붙들고 있으면 충돌한다.
남의 영역 폴더를 고쳐야 하면 먼저 말한다.

---

## 5. 콘텐츠 데이터

```
data/drafts/ → data/candidates/ → data/approved/ → generated/runtime/
```

- `data/approved/`로 옮기는 것은 **사람만** 한다. AI가 스스로 승인하지 않는다.
- `generated/runtime/`은 커밋하지 않는다. `npm run data:build`로 언제든 재생성한다.
- 승인이 끝난 `data/candidates/`의 후보와 `reports/`의 보고서는 **정리한다.**
  `AGENTS.md` 7절의 *"실패했거나 사용하지 않기로 한 AI 초안을 계속 누적하지 않는다"* 에 따른다.
  지워도 Git 이력에 남으므로 추적은 가능하다.

---

## 6. 에셋과 라이선스

**리소스를 추가하는 커밋에서 `docs/submission/CREDITS.md`에 같이 기록한다.**

외부 에셋의 출처와 라이선스 명시는 대회 제출 필수 요건이고, AI로 만든 에셋은 사용한 도구와
프롬프트까지 적어야 한다. 마감에 몰아서 정리하면 어떤 프롬프트를 썼는지 기억나지 않는다.

기록할 항목: 파일명 / 종류 / 제작 방법(직접·AI 생성·외부) / 도구 / 프롬프트 / 출처 URL / 라이선스

폰트는 특히 주의한다. 무료 폰트도 **웹 임베딩 허용 여부**가 갈린다.

## 7. 구현 규칙 (개발)

- 변경 가능한 게임 데이터를 코드에 하드코딩하지 않는다. (`DEC-PIPELINE-016`)
- 필수 데이터 누락을 코드 기본값으로 숨기지 않고 검증 오류로 보고한다.
- `api/`의 핸들러는 **표준 웹 `Request`/`Response`만** 사용한다. 특정 호스팅 업체 전용 헬퍼를
  쓰면 배포처를 바꿀 때 다시 짜야 한다.
- 엔딩 시스템 프롬프트는 `schema/ending_prompt_system.md` 한 곳에서 읽는다. 코드에 문장을
  복사하지 않는다. (`DEC-PIPELINE-012`)

## 8. 작업 기록

### 자동 (손댈 것 없음)

`docs/progress/PROGRESS.md`는 Git 커밋 이력에서 자동 생성한다. **직접 편집하지 않는다.**
push하면 CI가 갱신해서 `[Docs] PROGRESS.md 갱신 [skip ci]` 커밋을 원격에 올린다.

**그래서 작업을 시작할 때 항상 `git pull` 부터 한다.**
안 하면 내 로컬에는 없는 봇 커밋 위에 작업하게 되고, 다음 push가 막히거나
같은 파일을 두 번 생성해 충돌한다.

```bash
git pull            # 작업 시작할 때마다
npm run progress    # 로컬에서 미리 보고 싶을 때만. 평소엔 CI가 한다
```

### 수동 (선택)

커밋 메시지에 담기 어려운 맥락 — 왜 그렇게 했는지, 뭘 시도했다 접었는지 — 은
`docs/progress/sessions/<본인>.md`에 남긴다. **사람마다 파일이 달라서 충돌하지 않는다.**

8/8 제출 자료의 「AI 활용 기술 문서」와 「팀원 롤 기술서」를 쓸 때 이 기록이 재료가 된다.
그때 기억으로 복원하려 하면 대부분 잃어버린다.

## 9. 막혔을 때

기획 결정이 서로 안 맞거나, 모호하거나, 규칙이 없거나, 구현이 곤란하면
**임의로 CSV 열을 추가하거나 코드에 예외를 만들지 않는다.**

작업을 멈추고 `AGENTS.md` 5절의 절차에 따라 문제 유형·관련 DEC·영향 범위·대안을 정리해
기획 책임자에게 보고한다. 확정을 받은 뒤에 다시 시작한다.
